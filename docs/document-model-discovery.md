# Document model discovery

A package's document models are found from its model directories. There is no registration: `powerhouse.config.json` no longer has `definitionSources`, and `--code-first` only chooses how `ph generate document-model --name` creates a new model.

## Rules

Discovery reads `documentModelsDir` (default `./document-models`) and classifies each immediate directory `<name>/`:

| Directory holds                                                                  | Meaning                                                                                                                                                                        |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `<name>.json`                                                                    | A schema-first model. The file is the model, even when it cannot be read or parsed; the error is reported, and the directory is never read as code-first.                      |
| `gen/` or `v<N>/gen/`, without `<name>.json`                                     | Generated schema-first code whose specification is missing. Its generated modules stay exported, nothing is pruned, and `ph model check` warns (`PH-PKG-STORED-SPEC-MISSING`). |
| One `index.ts`, `index.mts`, `index.tsx`, `index.js`, `index.mjs` or `index.jsx` | A code-first model directory. Its exports are loaded; a directory whose entry exports no model is not a model.                                                                 |
| Several of those entry files                                                     | An error (`PH-CONFIG-SOURCE-INVALID`) naming them.                                                                                                                             |
| None of the above                                                                | No model. A `defineDocumentModel` call in it is reported as `PH-PKG-DEFINITION-UNREGISTERED`, with the entry to add.                                                           |

Discovery never reads the generated barrels (`document-models/index.ts`, `document-models.ts`, `upgrade-manifests.ts`). A model directory, or an entry, whose real path leaves the package is refused. Code-first directory aliases that reach the same module, including in-package symlinks, are loaded once.

Codegen generates a stored model inside `documentModelsDir`, next to its specification, and always writes the barrels to `./document-models`, the package's `document-models` subpath. In `./document-models`, generated code imports models through the `document-models/*` alias as before. In any other `documentModelsDir`, where no alias exists, generated model code, editors and the barrels import models by relative path.

## Generation

Every generation command (single model, `--all`, editors, `ph generate`, Vetra's processor) loads the whole inventory first and finishes through one barrel writer, so both styles are exported once each. When an entry cannot be loaded or the declaration scan finds a model that no entry exports, nothing is written. A model directory that is unreadable, or whose entry exports no model, keeps every manifest entry. The writer rebuilds the barrels on each run; it refuses to remove a statement it did not write, and it keeps an existing `export { documentModels } from "./document-models.js"` without adding one elsewhere.

## Converting a schema-first model

`ph migrate --document-models` (or `--document-model <dir>`) turns a stored model directory into the layout `ph generate document-model --code-first` scaffolds:

- `index.ts` materializes the family and exports each version, the latest one and the upgrade manifest.
- `upgrades/index.ts` declares the manifest. The existing `upgrades/v<N>.ts` transitions are kept.
- `v<N>/definition.ts` declares the state types, the enums and the inputs several modules share. `v<N>/index.ts` lists the version's modules.
- `v<N>/modules/<module>.ts` declares the inputs only its own operations use and holds each operation, and each reducer body moves into its operation's `reduce` with the helpers from its reducer file. An input stays in the definition when the reducer code already uses its name. Errors come from the operation's context. A `v<N>/errors.ts` is written only for error classes used outside a reducer that declares them.
- The custom code in `src/` moves into `v<N>/`, beside the definition. The generated code loaded `src/utils.ts` and `src/index.ts` with the model; afterwards only `compat/v<N>` loads them, so the migration is refused when one of them, or a file only they import, runs a statement for its effect when it loads (such as `registry.set(...)`), unless a reducer or an upgrade transition (`upgrades/v<N>.ts`) imports that file too. Declarations, and values such as `new Map()` or `new Set(["a"])` that call nothing else, are allowed. An import of a package or an import alias that binds nothing (`import "pkg"`, `import {} from "pkg"`) and `export * from "pkg"` in those files are refused the same way. Custom files anywhere in the model folder are checked; only the files the model keeps loading (the model's `index.ts`, the upgrade `index.ts`, `upgrade-manifest.ts`, `versions.ts` and `v<N>.ts` transitions, and each version's `index.ts`, `actions.ts`, `module.ts`, `utils.ts`, `hooks.ts` and `gen/`) are not. A tsconfig `paths` alias that maps to the same path from the project root, such as `scalars/*`, is followed. A named import or re-export (`export { x } from`) of a module the migration does not resolve, such as a package, a `package.json` `#imports` alias or another tsconfig `paths` alias, is not followed: if that module runs code when it loads and only those files load it, that code no longer runs with the model.

`<name>.json`, `v<N>/gen/`, `src/` and the other generated files are removed. Code that used the names the generated code exported (types, action creators, hooks, guards, factories, zod schemas) keeps working through `compat/v<N>/index.ts`, which derives each name from the new model. Its types and schemas live in `compat/v<N>/schema.ts`, which reads the definition, and a module's inputs only when one of their schemas is asked for, so the model's own files can use them at runtime; a model file that reads one of the module's values, such as `actions`, from the compat barrel is refused, because the barrel reads the model. Imports of the removed files anywhere in the package, through a relative path, the `document-models` alias or the package's own name, are rewritten to it, and an import of `<name>.json` is refused. A `vi.mock` or `jest.mock` (or vitest's typed `vi.mock(import("…"))`) of the model's `index.ts` or of a generated file moves to the one file that now provides every name it replaces, usually `compat/v<N>`, when its factory has the form `async (importOriginal) => ({ ...(await importOriginal()), name: … })` and replaces only names that file exported. The spread may also be `await vi.importActual` or `jest.requireActual` of the same module, directly or through a `const` that nothing else reads, and the object may be returned after other `const` declarations. Any other mock of those files is refused, because the file it would move to also holds other files' names, and so are two mocks (or a mock and a `vi.unmock`) anywhere in the package that name different modules and would move to the same file, because a test runner keeps one mock per module and a test shares its setup files' mocks. Mock calls through `vi`, `vitest` or `jest`, including one imported from the framework under another name, are recognized however their callee is spaced or commented, and a typed `vi.unmock(import("…"))` counts like a string one. Any other complete string, or template literal without substitutions, that names a removed file (or, in a file the migration moves, any file it would stop naming), such as a mock target held in a variable, passed through `.call` or another call, spread, chosen by a condition, or written through a namespace (`testApi.vi.mock`), a local variable (`const v = vi`) or a `vi` re-exported from another file, is refused, since the migration cannot tell how the string is used; this includes a string that only mentions the path, such as an assertion on it. An import of a replaced file with a query or fragment, such as `?raw`, is refused, since it would apply to different code; a moved file keeps its query. A percent-encoded path naming a moved or replaced file is refused rather than rewritten. A path the code computes, such as a template with substitutions, a concatenation, pieces joined at runtime, a helper's result or a value read from a data file, is not resolved, rewritten or refused, and can break after the migration. A moved mock also replaces its names for code that imported them from another generated file, such as `v<N>/gen/creators.ts` behind the model's `index.ts`. Code that reads `<name>.json` from disk through a path it computes, such as a test that joins path segments to compare the stored reducers with `src/`, is not detected and stops finding the file; a read that names the file in one string literal is refused. The model's `index.ts` now exports the family instead of the latest version's generated names, so another package that imported those names from `<package>/document-models/<name>` must import them from `<package>/document-models/<name>/compat/v<N>`.

A code-first model stores each module and operation under the PascalCase of its key (`SET_LABEL` becomes `SetLabel`); action types do not change. The `documentModel` that `compat/v<N>` exports keeps the names the schema-first specification stored, so code that reads them, for example as action types, works as before.

The CLI checks static package imports and exports and TypeScript path mappings before replacing model files, including runtime targets in build output directories. Rewritten imports use relative paths because the old alias might not map the replacement file. A mapping it cannot rewrite safely, including conditions that select different source and runtime files, causes an unchanged refusal. Use a relative import to the original target before migrating that model.

The operations object must be directly exported under the name imported by the generated reducer and contain exactly one plain member for each stored operation. Export aliases, spreads, extra members, accessors, computed keys and duplicate members are refused so their bindings, initialization or overrides are not lost. Other objects in the source file are preserved.

Before a model is kept, it is loaded again as `ph model inspect` loads it, and each version must have the stored definition: the same types, initial state, action types, scopes, inputs and errors. Otherwise its files are restored. IDs, the stored names of modules and operations, and the reducer text in the specification are not kept. Afterwards the barrels are regenerated as above. `--dry-run` prints the diff instead of writing it.

Unused value imports in moved model code remain in place because importing a module can initialize it. Every separate subgraph factory module stays loaded in its original order, preserving top-level initialization and re-export dependencies. A schema module with runtime imports beyond `graphql-tag` is refused unchanged; move those imports to the entry module while preserving their order before migrating. Resolvers with unannotated parameters, receiver reads, or yields that depend on context are refused before they move to class members, including nested callbacks and context supplied by `satisfies`, type assertions, and `ThisType`. Move those callbacks into explicitly typed helpers outside the resolver map. Static reader detection includes percent-encoded paths. A factory with other readers is refused if moving its resolvers would add exports, since that can change namespace imports or make barrel exports ambiguous. Move its shared declarations into a separate helper while preserving the factory module's exports before migrating. When a factory needs an imported value that the entry imports only as a type, migration refuses; use a runtime import that preserves initialization order before retrying. Reusing an earlier entry import is also refused when its runtime initialization order cannot be proved, including ordinary imports that a compiler may erase because only types use them. Give shared dependencies an explicit initialization order before retrying.

Model and subgraph migrations refuse output paths that are symbolic links or pass through a linked directory. Replace those links with regular project files or directories before migrating. Preview runs report the same restriction.

Subgraph migration preserves named function expressions and initialization reads, including getters whose results are unused. Factory-local functions keep their names and constructor behavior and remain separate for each subgraph instance. Type annotations that depend on factory-local values are refused when those values would become private fields. The migration keeps resolver factory files with other complete literal-path readers, including paths stored in variables. Merged declarations needed by moved resolvers are refused; move them into a separate imported helper before migrating. Additional reads of the factory binding from the entry or factory file are refused before removing that binding. A factory declared in a shared entry module is also refused, to preserve its exports. Dynamic reads and package or alias paths to the SDL module are refused before replacing its exports.

Referenced field and subscription resolvers are supported when immutable `const` aliases lead to an arrow function, including through imports. They keep all four GraphQL arguments, even when their types declare fewer. Mutable references, referenced `{ resolve }` field configs, and nonliteral Query or Mutation maps are refused because migration cannot preserve their receiver and function-selection timing across GraphQL engines. Use a literal map with inline arrows or immutable arrow references that capture their dependencies explicitly. The CLI marks any necessary compatibility casts while keeping checks on declared parameters and return values; `--strict-resolvers` leaves the type errors visible instead. A referenced `__resolveType` is refused because a code-first callback cannot supply GraphQL's fourth `abstractType` argument. A named recursive function that captures factory values is also refused; move it outside the factory and pass those values explicitly.

A reducer with a named function expression, its own `arguments`, or parameters beyond state, action and dispatch is refused. Call that logic from an immutable `const` arrow helper and reference the arrow from the operations object. Referenced reducers must resolve to an arrow through immutable bindings, including imports; ordinary functions and mutable references are refused because their receiver or selected callable could change. Moved model source files, including sibling helpers, and subgraph entry or resolver factory files that call direct `eval` are refused, because migration can change the bindings and arguments it reads. Model helpers and resolver code that read `import.meta` are refused when migration would move them to another file, because relative asset URLs could change. Keep location-dependent code in a helper file that the migration does not move. An import used only for the side effects of a replaced file is also refused; move the initialization into a helper file that the migration keeps.

The migration refuses a model it cannot convert faithfully, and says why. For example, it refuses a reducer that calls another reducer through `this`, an import of a generated name that nothing provides any more, or a `require` of a generated file, because what replaces it imports `document-model`, which has no CommonJS entry. A type that has the name of a scalar, such as `Address`, is refused unless `--rename-conflicting-types` is given. That flag renames the type by prefixing the model's name (`InvoiceAddress`), which changes its GraphQL name; `compat/v<N>` keeps its TypeScript name.

A required input field with a default, such as `name: String! = "untitled"`, becomes optional for a code-first caller, and the code-first runtime does not fill in the default, so the reducer receives `undefined`. A reducer that read the field as always set no longer type-checks. The migration lists each such field in a note; handle the missing value in the reducer.

## Reports

`ph model check --json` and `ph model inspect --json` print `formatVersion: 2`. Version 2 changes `sourceSet`:

```jsonc
// formatVersion 1
"sourceSet": { "mode": "code-first", "origin": "config", "digest": "sha256:…", "sources": [ … ] }
// formatVersion 2
"sourceSet": {
  "origin": "discovery",
  "documentModelsDir": "./document-models",
  "digest": "sha256:…",
  "sources": [{ "specifier": "./document-models/todo/index.ts" }],
  "stored": [{ "specifier": "./document-models/test-doc/test-doc.json" }]
}
```

The only skip reason is `no-document-models`. Definition digests, identities and the other report fields are unchanged.

## Updating testing projects

`definitionSources` was experimental and needs no migration support. When updating a testing project, delete the obsolete key from `powerhouse.config.json` and expose each code-first model through its model directory's `index.ts`. Discovery ignores the old setting; it does not select models, create wrappers, or require `ph migrate`.

Built packages continue to load through the `document-models` subpath as before.
