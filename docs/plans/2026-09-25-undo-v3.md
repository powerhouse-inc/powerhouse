# Plan: Undo v3, id-targeted retraction

Date: 2026-09-25
Status: proposal, questions resolved, not started

## Overview

An UNDO is stored as a NOOP whose `skip` of 1 retracts the operation
positionally before it. The NOOP names no target, so its meaning depends on
where it lands. A reshuffle can hand the NOOP a different skip, a trivial
append keeps the sender's skip against the receiver's own rows, and four rules
for which operations a stream applies disagree on streams the executor
produces. Replicas derive different states from the same operations, a
replica can lose one of its own operations for good, and REDO cannot succeed
on base-reducer 2.

This plan adds a third undo protocol, selected per document at creation, in
which a retraction names its target by action id and `skip` is only a
reshuffle's positional rewind. Documents on base-reducer 1 and 2 keep deriving
exactly as they do today.

We propose `protocolVersions["base-reducer"] = 3` as the detection mechanism,
a stored `RETRACT { target }` action that UNDO and REDO resolve to, one
derivation rule in shared (`positionalOperations`, `retractedActionIds`,
`appliedOperations`) used by every consumer that derives state or order,
receiver-derived skips and receiver-local hashes on the load path, and an
expression index on the operation table so the executor finds retractions
without reading the whole stream. Base-reducer 3 is version 3 of the
`base-reducer` capability of [peer protocol
agreement](2026-09-25-peer-protocol-agreement.md), which selects it only where
every member supports it and holds such documents from peers that do not.
Re-sending lost operations is a separate, parallel track.

## Current behaviour

A stream is a list of rows `(index, skip, action)`. `skip = k` retracts the k
rows logically before the row. Base-reducer 2 writes an UNDO as a NOOP with
skip 1 and derives state with `garbageCollectV2`, which counts trailing NOOP
chains by type and ignores `skip`.

| # | Defect | Pinned in |
|---|---|---|

| 2 | A peer's UNDO on a trivial append keeps its sender-relative skip and retracts the receiver's own unseen row. Trivial appends are not echoed, so the sender never learns. | `load-append-undo.test.ts`; `lost-operation-resend.test.ts` (#6b) |
| 3 | The v2 reducer reads a reshuffle-head NOOP's skip k as a one-operation undo. Served state, cold rebuild and replay agree on the wrong state, and a re-appended row is stored with `Module "x" already exists`. | `load-noop-head.test.ts`; `effective-ops-rules.test.ts` (iv) |
| 4 | `garbageCollect`, `processSkipOperation`, `garbageCollectV2`/`undoOperationV2`, and `supersededBy` disagree. | 5 | A replica that lost its own operation never gets it back: every outbox excludes rows from the peer it serves (`excludeSourceRemote`), and a fresh channel's `sinceTimestampUtcMs` filters it out. `backfillDocument` on a hold release skips the timestamp filter but still excludes the source. | `lost-operation-resend.test.ts` (#6, #6c) |

The common root is that an UNDO is a relative position with no target, and
the trivial-append path reuses the sender's skips verbatim.

Peer protocol agreement supplies the version machinery. The `base-reducer`
entry of `PEER_CAPABILITIES` supports `[1, 2]` and prefers 2. Selection picks
a new document's versions from its parent's collections, the outbox gate holds
a document from a peer without its versions (`SyncHold`), receipt and the
executor refuse rows at an unsupported version, and startup refuses a store
holding one.

## Design

### Detection

The undo protocol is the document's base-reducer version, fixed by
CREATE_DOCUMENT and part of the derived document id under the default
signature policy.

```ts
export type BaseReducerVersion = 1 | 2 | 3;

export function baseReducerVersion(header: PHDocumentHeader): BaseReducerVersion {
  const version = header.protocolVersions?.["base-reducer"];
  if (version !== 1 && version !== 2 && version !== 3) {
    throw new Error(`Document ${header.id} carries no supported base-reducer protocol version`);
  }
  return version;
}
```

Shared narrows the version and nothing more. Whether this reactor runs it is
agreement's existing executor check, which reads the local set through
`localSupports` and refuses with `UnsupportedProtocolVersionError`.

Every comparison of the form `protocolVersion >= 2` or `< 2` becomes a
`switch` over `BaseReducerVersion`: `processUndoRedo`, the two branches in
`baseReducer`, and workflow's `effectiveOperations`. The executor and the
write cache pass the version through. Version 2 branches stay byte-for-byte.

The stored operation also marks itself: `RETRACT` is a new base action type,
valid only in a base-reducer 3 stream.

```
base-reducer 1, 2   UNDO stored as NOOP with a positional skip; RETRACT refused
base-reducer 3      UNDO and REDO stored as RETRACT; NOOP is a plain no-op action
```

`RETRACT` and the document-scope action types join the reserved operation
names.

```ts
export const RESERVED_OPERATION_NAMES = [
  "UNDO", "REDO", "SET_NAME", "SET_PREFERRED_EDITOR", "NOOP", "RETRACT",
  "CREATE_DOCUMENT", "DELETE_DOCUMENT", "UPGRADE_DOCUMENT",
  "ADD_RELATIONSHIP", "REMOVE_RELATIONSHIP", "UPDATE_RELATIONSHIP", "PURGE_DOCUMENT",
] as const;
```

The document-model editor reducers refuse these names through
`validateOperationName`. Codegen refuses a spec with an operation name that
`isReservedOperationName` matches, so a spec written outside the editor
cannot declare one either.

### Peer capability

The `base-reducer` entry of `PEER_CAPABILITIES` reads a new reactor flag,
`undoV3`.

```ts
{
  kind: "protocol",
  name: "base-reducer",
  baseline: [1, 2],
  supported: (flags: PeerCapabilityFlags) => (flags.undoV3 ? [1, 2, 3] : [1, 2]),
  preferred: (flags: PeerCapabilityFlags) => (flags.undoV3 ? 3 : 2),
  optional: false,
}
```

`undoV3` joins `ReactorFeatureFlags`, `FLAG_PREREQUISITES` with no
prerequisites, `resolveFeatureFlags`, and the hosts' flag configuration
(switchboard's feature flags, the Connect runtime config schema and its
documentation). The reactor passes its resolved flags to the capabilities,
so agreement does the rest. A peer that announces nothing gets the baseline
and never receives a base-reducer 3 document.

### Data shapes

```ts
export type RetractActionInput = { target: string };
export type RetractAction = Action & { type: "RETRACT"; input: RetractActionInput };

export const retract = (target: string, scope = "global") =>
  createAction<RetractAction>("RETRACT", { target }, undefined, RetractActionInputSchema, scope);
```

`target` is an action id in the same (document, scope, branch). UNDO and REDO
keep their inputs (`{ count }`); base-reducer 3 accepts only count 1.

```
Operation.skip in base-reducer 3
  = the rewind of a reshuffle this replica wrote; 0 otherwise
  never read from a peer, never an undo
```

```sql
create index "idx_operation_retracts" on "Operation"
  ("documentId", "scope", "branch", (action->'input'->>'target'))
  where action->>'type' = 'RETRACT';
```

### The rule

One module in shared. Consumers that need order use `positionalOperations`;
consumers that need state use `appliedOperations`.

```ts
export function positionalOperations<T extends OperationIndex>(stream: readonly T[]): T[] {
  return garbageCollect(sortOperations([...stream]));
}

export function retractionTarget(operation: Operation): string | undefined {
  return operation.action.type === "RETRACT"
    ? (operation.action.input as RetractActionInput).target
    : undefined;
}

export function retractedActionIds(rows: readonly Operation[]): Set<string> {
  const present = new Set(rows.map((operation) => operation.action.id));
  const targetOf = new Map<string, string>();
  for (const operation of rows) {
    const target = retractionTarget(operation);
    if (target !== undefined && target !== operation.action.id && present.has(target)) {
      targetOf.set(operation.action.id, target);
    }
  }
  for (const id of onCycles(targetOf)) {
    targetOf.delete(id);
  }

  const retractors = new Map<string, string[]>();
  for (const [retraction, target] of targetOf) {
    retractors.set(target, [...(retractors.get(target) ?? []), retraction]);
  }

  const live = new Map<string, boolean>();
  const isLive = (id: string): boolean => {
    const known = live.get(id);
    if (known !== undefined) return known;
    const result = !(retractors.get(id) ?? []).some(isLive);
    live.set(id, result);
    return result;
  };
  return new Set([...present].filter((id) => !isLive(id)));
}

export function appliedOperations(stream: readonly Operation[]): Operation[] {
  const rows = positionalOperations(stream);
  const retracted = retractedActionIds(rows);
  return rows.filter(
    (operation) =>
      !retracted.has(operation.action.id) &&
      operation.action.type !== "RETRACT" &&
      !isDenied(operation),
  );
}

export function deriveScope(initial: PHDocument, stream: readonly Operation[], reduce: Reduce): PHDocument;
```

An action is live if and only if no live retraction names it. Liveness
depends on the set of rows, not their order. A retraction whose target is
absent does nothing until the target arrives; a retraction on a cycle does
nothing. The implementation walks the chains iteratively. `deriveScope` runs
the reducer over `appliedOperations`; a row whose reducer call throws applies
nothing.

A stored `error` is diagnostic in base-reducer 3. Derivation never reads it
and never writes it into rows other than the one being appended.

### Undo and redo resolution

```ts
export function undoTarget(stream: readonly Operation[]): string | undefined {
  const rows = positionalOperations(stream);
  const retracted = retractedActionIds(rows);
  for (let i = rows.length - 1; i >= 0; i--) {
    const operation = rows[i];
    if (retracted.has(operation.action.id) || !isContent(operation)) continue;
    return operation.action.id;
  }
  return undefined;
}

export function redoTarget(stream: readonly Operation[]): string | undefined {
  const rows = positionalOperations(stream);
  const retracted = retractedActionIds(rows);
  const byId = new Map(rows.map((operation) => [operation.action.id, operation]));
  for (let i = rows.length - 1; i >= 0; i--) {
    const operation = rows[i];
    if (retracted.has(operation.action.id)) continue;
    const target = retractionTarget(operation);
    if (target === undefined) {
      if (isContent(operation)) return undefined;
      continue;
    }
    if (isContent(byId.get(target))) return operation.action.id;
  }
  return undefined;
}
```

UNDO retracts the last applied operation that is not a retraction. REDO
retracts the last live undo, unless applied content follows it. `isContent`
holds for a row that is not a RETRACT or a NOOP, is not denied, and applies
without a throw in `deriveScope`.

```
a b                 UNDO -> RETRACT(b)      applied: a
a b R(b)            UNDO -> RETRACT(a)      applied: -
a b R(b) R(a)       REDO -> RETRACT(R(a))   applied: a
a b R(b) R(a) R'    REDO -> RETRACT(R(b))   applied: a b
a b R(b) c          REDO refused: c follows the undo
```

The reducer resolves UNDO and REDO to a RETRACT, as base-reducer 2 resolves
UNDO to a NOOP, so the executor's synthesize-and-sign path is unchanged.

```ts
case 3: {
  if (action.input.count !== 1) {
    throw new Error(`${action.type} on base-reducer 3 takes count 1`);
  }
  const operations = document.operations[action.scope] ?? [];
  const target = action.type === "UNDO" ? undoTarget(operations) : redoTarget(operations);
  if (target === undefined) {
    throw new Error(`Cannot ${action.type === "UNDO" ? "undo" : "redo"}: nothing to ${action.type.toLowerCase()} in scope history`);
  }
  return { document, action: retract(target, action.scope), skip: 0, reuseLastOperationIndex: false };
}
```

Both throws are the reducer's plain errors, as on base-reducer 2. The job
fails, and `JobRollbackSignal` rolls back every write of the job, including
earlier actions of a multi-action job.

After `baseReducer` appends the row, base-reducer 3 re-derives the scope when
the row rewinds, retracts, or is already retracted, and otherwise applies the
one action.

```ts
const operations = next.operations[scope];
const rebuild =
  skip > 0 ||
  action.type === "RETRACT" ||
  retractedActionIds(positionalOperations(operations)).has(action.id);
next = rebuild ? deriveScope(next, operations, reduce) : reduceOne(next, action);
```

`processSkipOperation`, `garbageCollectV2`, `mapSkippedOperationsV2`,
`undoOperationV2` and the clipboard are not used on base-reducer 3.

### Where the rule applies

| Consumer | Base-reducer 3 |
|---|---|
| `baseReducer` | as above |
| executor, `prepareRegularWrite` | full history when `needsFullHistory`; the reducer does the rest |
| `canBatch` | a RETRACT is never batched |
| write cache cold rebuild at head | one pass over `appliedOperations` |
| write cache keyframe and warm rebuilds | the whole log when a row after the keyframe has skip > 0, is a RETRACT, or is named by a retraction |
| read-model sweeps and boot replay through `writeCache.getState` at a revision | `deriveScope` over the stream up to that revision |
| `selectLoadWrites`, `executeLoadJob` | `positionalOperations` only; see Load path |
| `positionByTimestamp`, `reevaluateDocument`, `firstOutOfOrderPair` | `positionalOperations`, unchanged; RETRACT rows move as rows |
| `walkByPosition`, the auth decision model's evaluated-scope apply | `positionalOperations`; re-derive on a RETRACT or a retracted row; never read `error` |
| `replayDocument`, `replayDocumentVersioned`, `baseLoadFromInput`, `baseLoadFromInputVersioned` | `positionalOperations`, then the reducer; `ignoreSkipOperations` has no effect; PURGE_DOCUMENT applies as a deletion |
| UNDO/REDO preconditions | `undoTarget`, `redoTarget` |
| workflow `effectiveOperations` | `appliedOperations`; one UNDO per retracted target |
| reactor-browser `unsupportedBatchActions` | RETRACT joins; `predictionProtocolVersion` stays 2, since no batched action depends on the version |
| reactor-drive `NodeProcessor` | ignores RETRACT, as it ignores UNDO |

`prepareRegularWrite` invalidates the write cache, forcing a cold rebuild,
when `isUndoRedo(action) || skip > 0`. On base-reducer 3 the condition is
`needsFullHistory`, with `targeted` from `findRetractionsOf` over the job's
action ids.

```ts
function needsFullHistory(write: PendingWrite, targeted: ReadonlySet<string>): boolean {
  return (
    write.skip > 0 ||
    isUndoRedo(write.action) ||
    write.action.type === "RETRACT" ||
    targeted.has(write.action.id)
  );
}

interface IOperationStore {
  findRetractionsOf(documentId: string, scope: string, branch: string, actionIds: string[], signal?: AbortSignal): Promise<Set<string>>;
}
```

`findRetractionsOf` returns the ids among `actionIds` that a stored RETRACT
names, in the shape of `findOperationIds`. The executor calls it inside the
job transaction under the document lock, so it needs no read watermark; the
write cache calls it for the keyframe and warm fallbacks.
`KyselyOperationStore` answers from `idx_operation_retracts`, and
`HypercoreOperationStore` implements it beside `findOperationIds`.

### Load path

In base-reducer 3 a skip is never an undo, so a reshuffle reasons about
positions only.

```
selectLoadWrites, base-reducer 3
  supersededBy           unchanged: positional coverage
  undoneActionIds        not built; a row covered only by a rewind is lost and re-applied
  incomingOpsToApply     unchanged: dedup by action id within the conflict window

executeLoadJob, base-reducer 3
  trivial append         every row written with skip 0
  reshuffle              reshuffleByTimestamp: skipCount on the first row, 0 on the rest
  NOOP skip restoration  not applied
  source row             passed as replayOptions.operation without hash or skip
```

A receiver's skip describes the receiver's own rewind, and a trivial append
rewinds nothing. Echo suppression by `sourceRemote` is unchanged; replicas
that hold the same rows derive the same retractions without an echo. An
incoming row's `error` is not stored, as today.

Hashes are receiver-local: the reducer hashes the receiver's derived state
and never reuses the sender's `hash`. Write cache rebuilds replay the
replica's own rows and keep reusing their stored hashes, and replay with
`checkHashes` compares the derived state with the last stored row, which is
the replica's own.

### Signing and replay protection

```
RETRACT preimage (v2 tuple, unchanged scheme)
  ["v2", documentId, branch, scope, "RETRACT", id, timestampUtcMs, { target }, user.address, user.networkId, user.chainId, app.key]
```

- The target is in `input`, so the signature covers it, and the preimage binds
  document, branch and scope. A RETRACT cannot be moved to another stream, and
  its target is looked up only in its own stream.
- Submitted RETRACT: stored as submitted, under the author's signature.
- Submitted UNDO or REDO: resolved by the reducer and signed by the reactor
  through `signSynthesized` under `synthesizedActionId(submitted.id)`, as the
  NOOP is today.
- Replay: `DUPLICATE_ACTION` refuses any action id already in the stream,
  including a retracted one and every RETRACT. Retraction is by action id, so
  a re-delivered or re-appended copy of a retracted action stays retracted.
- Revival happens only through a live RETRACT naming the retraction. REDO is
  therefore a new, signed action.

```
execute
  RETRACT, base-reducer 1 or 2               ReservedActionError
  RETRACT, scope "auth" or "document"        ReservedActionError
  RETRACT, target absent from the stream     RetractionRefusedError, "target-missing"
  RETRACT, target already retracted          RetractionRefusedError, "target-retracted"

load
  RETRACT, base-reducer 1 or 2               ReservedActionError
  RETRACT, scope "auth" or "document"        ReservedActionError
  RETRACT, target absent                     admitted; does nothing until the target arrives
```

The executor's mutation check that refuses a purge marker refuses these
RETRACTs too, the load path gains the same check, and `DocumentActionHandler`
refuses RETRACT beside `PURGE_DOCUMENT`. A load refused with
`ReservedActionError` dead-letters as `RESERVED_ACTION`, which quarantines
the document. `RetractionRefusedError` (`documentId`, `target`, `reason`) is
new: it joins the terminal allow-list in `JobResultHandler`, and
`classifyJobFailure` maps it to a new `SyncOperationErrorType`,
`RETRACTION_REFUSED`.

### Erasure

A purge deletes every row of the document, and the index entries with them.
The purge marker, the only row of a purged stream, is in the document scope,
where RETRACT is refused, so `undoTarget` and `redoTarget` never see it. A
RETRACT that arrives after the purge is refused with `DocumentPurgedError`
and dropped, like any operation. A purged document's versions are
`{ "document-purge": 1 }`, so every base-reducer dispatch sits behind the
existing marker checks (`isPurgeMarker`, `executePurge`).

### Auth scope and decisions

- RETRACT on the auth scope is refused with `ReservedActionError` in the
  executor, and `assertAuthScopeActionAllowed` refuses it in shared as it
  does UNDO and REDO. The monotonic auth stream is never reshuffled and holds
  no retraction.
- Decisions see RETRACT as an operation type; a policy grants or refuses it
  like any other. A policy cannot condition on who wrote the target.
- The decision walk, DCB append conditions and re-evaluation read positions
  through `positionalOperations`, which is `garbageCollect`. In base-reducer 3
  that is exact, because only reshuffles write a skip.

## Backward compatibility and mixed versions

| Document | Writer | Reader | Behaviour |
|---|---|---|---|
| 1 or 2 | any | any | Unchanged, including the pinned defects. |
| 1 or 2 | peer sends RETRACT | stage 1+ | Refused with `ReservedActionError`; the `RESERVED_ACTION` dead letter quarantines the document. Only a faulty peer sends it. |
| 1 or 2 | peer sends RETRACT | before stage 1 | Stored; generated reducers return state for an unknown type, so it applies nothing. |
| 3 | `undoV3` on | `undoV3` on | Base-reducer 3. |
| 3 | `undoV3` on | `undoV3` off, or without agreement | Not sent: the reader does not announce 3, or announces nothing and gets the baseline, and the gate holds the document. The hold releases with a whole-document backfill when the reader announces 3. |
| 3 | any | announces 3 but refuses it | Refused `UNSUPPORTED_PROTOCOL`, non-quarantining; the sender turns the refusal into a hold. Only a misconfigured peer reaches this. |
| 3 | `.phd` import | agreement, `undoV3` off | CREATE refused with `UnsupportedProtocolVersionError`. |
| 3 | `.phd` import | without agreement | Not prevented: the build reads version 3 as `>= 2` and runs base-reducer 2. |

Receipt judges every row, not only CREATE: a write from a peer that does not
announce the document's version is refused `PEER_PROTOCOL_UNSUPPORTED`. Every
hop's gate holds a base-reducer 3 document from a peer that does not support
it, so no base-reducer 3 stream holds rows written by a reactor that reads it
as base-reducer 2. A document created at 3 whose collection has an older
reactor behind a relay stays held at the relay until that reactor upgrades.
A document created without a parent takes the local preference, 3 with
`undoV3` on, and the gate holds it from any peer without 3.

Rolling back:

- Turning `undoV3` off over a store that holds base-reducer 3 documents
  refuses to start with `UnsupportedStoredProtocolError`, unless the host
  builds with `withUnsupportedStoredDocuments("read-only")`, which keeps those
  documents read-only.
- A build below stage 3 refuses to start over a store that ran
  `027_index_operation_retracts`, because its migrator finds an executed
  migration it does not know. Once stage 3 runs, it is the floor for binary
  rollback.

An existing document opts in by copy. `protocolVersions` is immutable after
CREATE and part of the derived id, so there is no in-place switch.
`createCopyHeader` keeps the source's versions, so a copy to 3 overrides the
key on the source it passes.

```ts
createCopyHeader(
  { ...source.header, protocolVersions: { ...source.header.protocolVersions, "base-reducer": 3 } },
  targetId,
  policy,
);
```

DriveClient's copy seeds the new document from the source's state
(`initialState: srcDoc.state`, no operations). History before the copy is not
undoable.

## Stages

One PR per stage. Stages 1 to 6 ship with `undoV3` off. Every stage leaves
base-reducer 1 and 2 unchanged. Tests enable the flag where they need it.

A "v3 twin" is the pinned scenario on a base-reducer 3 document in the same
file, with a peer's undo expressed as `retract(target)`. The v2 original is
pinned to base-reducer 2 explicitly, keeps `it.fails`, and is labelled as
base-reducer 2 behaviour. The flips per stage are in Pinned test accounting.

1. **Version gate.** `undoV3` declared, off, and read by the `base-reducer`
   capability entry. `BaseReducerVersion`, with `baseReducerVersion`
   accepting 1 and 2. Explicit version dispatch at the four sites. RETRACT
   refused with `ReservedActionError` on execute and load and in
   `DocumentActionHandler`. `RESERVED_OPERATION_NAMES` extended and the
   codegen check. The pinned v2 tests pin base-reducer 2 through
   `createCreateDocumentOperation` and `createPresignedHeader`.
   Flips: none.
2. **Shared rule and reducer.** `positionalOperations`, `retractedActionIds`,
   `appliedOperations`, `deriveScope`, `undoTarget`, `redoTarget`, `retract`
   and its schema; the base-reducer 3 branches; the replay paths.
   `baseReducerVersion` accepts 3. The reactor still refuses a version 3
   document without `undoV3`. Unit tests and the model-level property test.
   Flips: none.
3. **Execute path and retraction index.** Migration
   `027_index_operation_retracts`, `findRetractionsOf` in both stores,
   `needsFullHistory`, `canBatch`, RETRACT admission and
   `RetractionRefusedError`, UNDO/REDO synthesized as RETRACT, the one-pass
   cold rebuild, the keyframe and warm fallbacks, and the historical rebuild
   for read models.
   Flips: the stage 3 twins, plus a new (ii) twin in which UNDO, REDO, UNDO
   succeeds.
4. **Load path.** Receiver-derived skips, no NOOP skip restoration, no
   `undoneActionIds`, receiver-local hashes.
   Flips: the stage 4 twins.
5. **Decisions and re-evaluation.** `walkByPosition` and the auth decision
   model's evaluated-scope apply re-derive on a RETRACT or a retracted row and
   stop reading `error`; `positionByTimestamp` and `reevaluateDocument` move
   RETRACT rows as rows.
   Flips: the stage 5 twin.
6. **Client and API.** `IReactorClient.undo` and `redo`, new methods: on
   base-reducer 3 they resolve the target with `undoTarget`/`redoTarget` over
   `getOperations` and submit a signed RETRACT, so the author's signature
   covers the target; on 1 and 2 they submit UNDO and REDO. reactor-api
   accepts RETRACT; reactor-browser adds RETRACT to `unsupportedBatchActions`
   and exposes undo and redo availability; workflow's `effectiveOperations`
   gains its base-reducer 3 branch; academy docs describe base-reducer 3.
   Flips: none.
7. **Default on.** `undoV3` defaults on, so the capability announces and
   prefers 3. `selectProtocolVersions` picks 3 for a parented create where
   every member (the parent's collections and the parent drive's own
   collection) supports it, and otherwise the highest version they all
   support. The create paths that default
   `"base-reducer": 2` for a header with no versions keep that default.
   DriveClient's copy takes a `protocolVersions` override for copy-to-v3.
   Flips: none.

### Separate track: re-sending lost operations

Loss is not specific to undo. It follows from damaged stores, v2 documents,
and any future defect, and base-reducer 3 removes only the undo-driven cause.
We run it as a parallel track with its own plan, announced as agreement's
`sync.anti-entropy` feature, and name only its scope and tests here.

- **R1, anti-entropy.** Peers exchange a per-stream digest of positionally
  live operation ids, computed at or below `settledThrough`, on connect and
  with acks. On a mismatch the peer sends its positionally live rows for that
  stream, bypassing `excludeSourceRemote` and `sinceTimestampUtcMs`; the
  receiver's load dedups.
- **R2, fresh channels.** `sinceTimestampUtcMs` becomes a hint confirmed by
  an R1 digest exchange before a fresh channel trusts it.

## Migration

- Schema: one additive migration, `027_index_operation_retracts`, registered
  in the migrator. It creates `idx_operation_retracts` on `Operation` only;
  the executor and the write cache are its only readers. No backfill: no
  stored row is a RETRACT before stage 3. Once it runs, binary rollback below
  stage 3 is blocked.
- Documents: none. Base-reducer 1 and 2 documents keep their rule and their
  stored rows. Opting in is a copy.

## Test strategy

- **Unit, shared.** `retractedActionIds` over chains, redo of redo, cycles,
  self-targets, absent targets, and two retractions of one target.
  `undoTarget`/`redoTarget` against the stack table above.
- **Twins.** Each pinned scenario on base-reducer 3, as listed in the
  accounting.
- **One-rule agreement.** For every stream a twin produces: served state,
  cold rebuild, keyframe and historical rebuild, the reducer over the stored
  stream, `replayDocument` with `checkHashes`, and a `.phd` round trip all
  equal `deriveScope` over `appliedOperations`, and no row carries an error
  from applying an action twice.
- **Differential property test, model level.** Replicas as row lists; random
  execute, UNDO, REDO, RETRACT, partial and repeated delivery, and skewed
  timestamps; quiesce by full exchange. Local writes are positioned by
  timestamp, as `positionByTimestamp` does. Asserts equal live sets and equal
  order across replicas. A spike of this model with the rule above, over
  20,000 seeded three-replica trials, shows no live-set divergence. Order
  diverges in 2,315 trials when local writes append at the head regardless of
  timestamp, and in none when they are positioned.
- **Differential property test, reactor level.** The same generator at small
  bounds against in-process reactors connected by the test channel, seeded,
  printing the seed on failure.
- **Mixed fleets.** The `withPeerCapabilities` fleet harness with `undoV3` on
  and off: holds, releases with backfill, and `ReservedActionError` for a
  RETRACT into a base-reducer 2 document.
- **v2 regression.** The whole existing suite unchanged, plus a corpus of the
  pinned v2 streams with their served states, asserted equal before and after
  every stage.
- **Model checking.** Not planned. Bounded exhaustive enumeration of delivery
  orders (two replicas, up to four operations each) in the model harness
  covers the same ground.

## Decisions

1. **Per-document version plus an op type.** The document version selects one
   rule for the whole stream, so no stream mixes positional undo with
   retraction. The RETRACT type makes the stored intent self-describing. A
   per-op marker alone would leave v2 NOOP semantics live inside new streams.
   A field on the NOOP is rejected because base-reducer 2 restores skip 1 on
   a re-appended incoming NOOP and would turn it into a positional undo.
2. **`base-reducer`, not a new key.** The base-reducer version already
   selects the undo implementation. A separate `undo` key would behave the
   same on older reactors and add a second dispatch.
3. **Target by action id.** The operation id is derived from the action id
   within a stream, so they are equivalent in-stream. The action id is what
   the signer names and survives a branch merge.
4. **Set-based liveness.** Retraction depends on which rows are present, not
   their order, so reshuffles, clock skew and delivery order cannot change
   what is retracted. Cycles need forged ids and are made inert
   deterministically.
5. **Skip is positional and receiver-derived.** The receiver computes every
   skip from its own log. This removes defects 1 and 2 at their source and
   lets a reshuffle ignore undo entirely.
6. **REDO retracts a retraction.** No clipboard or derived stack is stored;
   the redo stack is read from the stream. Applied content after an undo ends
   the redo chain, matching base-reducer 1.
7. **UNDO and REDO remain.** They resolve to RETRACT in the reducer, keeping
   `undo()` callers and the synthesize-and-sign path working. RETRACT is the
   first-class form, and the client submits it so the author's signature
   covers the target.
8. **Absent targets.** Refused on execute, where the author must see the
   target. Admitted on load, where delivery order is not ours to choose; the
   set-based rule makes them effective when the target arrives.
9. **Base-reducer 2 frozen, including trivial-append skips.** We do not
   change its derivation or its write paths. Zeroing the sender's skip on v2
   non-NOOP rows would likely fix one v2 lost-operation case, but any v2
   change makes old and new reactors write different rows for the same input
   during rollout. The defects stay pinned as v2 behaviour.
10. **Peer protocol agreement, not rollout order.** A reactor without
    base-reducer 3 would read a version 3 document as base-reducer 2 and
    write positional NOOPs into it. As a version of a peer capability,
    base-reducer 3 is selected only where every member supports it and held
    from every peer that does not, at every hop. Mixed fleets stay safe
    without coordinating releases, and undo adds no sync code of its own.
11. **The capability entry changes in place; shared only narrows.** Support
    is read through `localSupports`, so no consumer needs the entry by name.
    Support gating stays in the reactor, where
    `UnsupportedProtocolVersionError` lives.
12. **An expression index, not a column.** The executor must know whether a
    row it is about to write is retracted without reading the whole stream on
    every re-append. An index over the action JSON needs no write-path
    change and no backfill, follows the existing protocol-versions index on
    `Operation`, and the store already filters on `action->>'type'`. A
    derived set in the write cache would need to survive keyframes.
13. **Hashes are receiver-local.** Set-based liveness lets a receiver's
    state at a row differ from the sender's, so a reused sender hash would
    fail replay with `HashMismatchError`. The signature does not cover the
    hash, so recomputing it changes nothing a peer verifies.
14. **Stored `error` is diagnostic.** A retraction can make an earlier failure
    succeed or a later success fail. Re-deriving keeps replicas that received
    rows in different orders equal.
15. **Refusals reuse the reserved-action path.** A RETRACT in a base-reducer
    1 or 2 document, or on the auth or document scope, is a reserved action,
    refused with `ReservedActionError` on execute and load. Only a faulty or
    forged peer sends one, so it quarantines like any reserved action; a
    silent drop would hide the fault. Target refusals are deterministic, so
    `RetractionRefusedError` is terminal rather than retried. Count and
    "nothing to undo" stay the reducer's plain errors, as on base-reducer 2,
    because shared cannot raise reactor errors.
16. **Erasure needs nothing of its own.** The index lives on `Operation`
    rows, which a purge deletes, and the marker lives in a scope where
    RETRACT is refused. Keeping the dispatch behind the marker checks avoids
    giving a purged document a base-reducer version it does not have.
17. **Resend is a separate track.** It is protocol-independent and needed for
    v2 documents and damaged stores whatever this plan does.
18. **Opt-in by copy only.** An in-place switch would contradict CREATE-fixed
    `protocolVersions` and the derived id, and a reshuffle could move rows
    across the switch.
19. **Copy seeds from state.** Replaying the source's history as fresh actions
    would attribute every copied operation to the copier. Seeding from state
    keeps authorship honest at the cost of undo reaching back past the copy.
20. **UNDO stays scope-wide.** It retracts the last applied operation by
    anyone, as today. Per-signer undo needs no protocol change later: a
    client can already submit a RETRACT naming its own last operation.
21. **No target-author condition yet.** A policy grants or refuses RETRACT as
    an operation type. Letting a policy compare the target's signer with the
    retractor needs the decision model to read the target, and is a
    follow-up.
22. **Reserved names cover every base and document-scope action, and codegen
    checks them.** The action type alone selects routing and the signed
    document id for document-scope actions, so a model operation with one of
    those names would be read as the base action. The editor's validation
    does not cover specs written elsewhere.
