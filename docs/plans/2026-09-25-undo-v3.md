# Plan: Undo v3, id-targeted retraction

Date: 2026-09-25
Status: proposal, questions resolved, not started

## Overview

An UNDO is stored as a NOOP whose `skip` of 1 retracts the operation
positionally before it. The NOOP names no target, so its meaning depends on
where it lands. A reshuffle can hand the NOOP a different skip, a trivial
append keeps the sender's skip against the receiver's own rows, and four rules
for which operations a stream applies disagree on streams the executor
produces. Replicas derive different states from the same operations, a
replica can lose one of its own operations for good, and REDO cannot succeed
on base-reducer 2.

This plan adds a third undo protocol, selected per document at creation, in
which a retraction names its target by action id and `skip` is only a
reshuffle's positional rewind. Documents on base-reducer 1 and 2 keep deriving
exactly as they do today.

We propose `protocolVersions["base-reducer"] = 3` as the detection mechanism,
a stored `RETRACT { target }` action that UNDO and REDO resolve to, one
derivation rule in shared used by every consumer that derives state or
order, receiver-derived skips and hashes on the load path, and an expression
index so the executor finds retractions without reading the whole stream.
Base-reducer 3 is version 3 of the `base-reducer` capability of [peer
protocol agreement](2026-09-25-peer-protocol-agreement.md), which selects it
only where every member supports it and holds such documents from peers that
do not. Re-sending lost operations is a separate, parallel track.

## Current behaviour

A stream is a list of rows `(index, skip, action)`. `skip = k` retracts the k
rows logically before the row. A load whose incoming rows all sort after the
receiver's head is a trivial append: the rows are appended as they arrive,
skips included. Any other load is a reshuffle: the receiver rewinds to the
earliest conflicting position, writes the rewind as the first re-appended
row's skip, and re-appends its own rows and the incoming ones in timestamp
order.

Base-reducer 2 writes an UNDO as a NOOP with skip 1 and derives state with
`garbageCollectV2`, which counts trailing NOOP chains by type and ignores
`skip`.

| # | Defect | Pinned in |

| 2 | A peer's UNDO, or any row carrying a skip, on a trivial append keeps its sender-relative skip and retracts the receiver's own unseen row. Trivial appends are not echoed, so the sender never learns. | `load-append-undo.test.ts`; `lost-operation-resend.test.ts` |
| 3 | The v2 reducer reads a reshuffle-head NOOP's skip k as a one-operation undo. Served state, cold rebuild and replay agree on the wrong state, and a re-appended row is stored with `Module "x" already exists`. | `load-noop-head.test.ts`; `effective-ops-rules.test.ts` (iv) |
| 4 | `garbageCollect`, `processSkipOperation`, `garbageCollectV2`/`undoOperationV2`, and `supersededBy` disagree. The common root is that an UNDO is a relative position with no target, and
the trivial-append path reuses the sender's skips verbatim.

## Design

### Detection

The undo protocol is the document's base-reducer version, fixed by
CREATE_DOCUMENT and part of the derived document id under the default
signature policy. `baseReducerVersion` in shared narrows its result and
throws a plain `Error` on a missing or unknown version; whether this reactor
runs a version is agreement's executor check.

```ts
export type BaseReducerVersion = 1 | 2 | 3;
export function baseReducerVersion(header: PHDocumentHeader): BaseReducerVersion;
```

Every comparison of the form `protocolVersion >= 2` or `< 2` becomes a
`switch` over `BaseReducerVersion`: `processUndoRedo`, the two branches in
`baseReducer`, and workflow's `effectiveOperations`. The executor and the
write cache pass the version through. Version 2 branches stay byte-for-byte.

The stored operation also marks itself: `RETRACT` is a new base action type.

```
base-reducer 1, 2      UNDO stored as NOOP with a positional skip; RETRACT is an inert row
base-reducer 3         UNDO and REDO stored as RETRACT; NOOP is a plain no-op action
auth, document scopes  RETRACT is an inert row in every version
```

An inert row applies nothing: generated reducers and `applyAuthAction`
return state unchanged for a type they do not know, `isDocumentAction`
excludes RETRACT, and the write cache and replay apply it through the same
reducers. In base-reducer 1 and 2, `garbageCollect` and `garbageCollectV2`
count it as an ordinary row, so an UNDO directly after it retracts nothing
visible. Older reactors store it the same way.

`RETRACT` joins `RESERVED_OPERATION_NAMES`. The document-model editor
reducers already refuse reserved names through `validateOperationName`;
codegen also refuses a spec with an operation name that
`isReservedOperationName` matches.

### Peer capability

The `base-reducer` entry of `PEER_CAPABILITIES` reads a new reactor flag,
`undoV3`.

```ts
{
  kind: "protocol",
  name: "base-reducer",
  baseline: [1, 2],
  supported: (flags: PeerCapabilityFlags) => (flags.undoV3 ? [1, 2, 3] : [1, 2]),
  preferred: (flags: PeerCapabilityFlags) => (flags.undoV3 ? 3 : 2),
  optional: false,
}
```

`undoV3` joins `ReactorFeatureFlags`, `FLAG_PREREQUISITES` with no
prerequisites, `resolveFeatureFlags`, and the hosts' flag configuration
(switchboard's feature flags, the Connect runtime config schema and its
documentation). The reactor passes its resolved flags to the capabilities,
so selection, the outbox gate, receipt refusal, executor refusal and the
startup check follow from the entry. A peer that announces nothing gets the
baseline and never receives a base-reducer 3 document.

### Data shapes

`target` is an action id in the same (document, scope, branch). UNDO and REDO
keep their inputs (`{ count }`); base-reducer 3 accepts only count 1.

```
Operation.skip in base-reducer 3
  = the rewind of a reshuffle this replica wrote; 0 otherwise
  never read from a peer, never an undo
```

```sql
create index "idx_operation_retracts" on "Operation"
  ("documentId", "scope", "branch", (action->'input'->>'target'))
  where action->>'type' = 'RETRACT';
```

### The rule

One module in shared. Consumers that need order use `positionalOperations`;
consumers that need state use `deriveScope`. The rule applies to every scope
except auth and document.

```ts
export function positionalOperations<T extends OperationIndex>(stream: readonly T[]): T[] {
  return garbageCollect(sortOperations([...stream]));
}

export function retractionTarget(operation: Operation): string | undefined {
  return operation.action.type === "RETRACT"
    ? (operation.action.input as RetractActionInput).target
    : undefined;
}

export function retractedActionIds(rows: readonly Operation[]): Set<string> {
  const present = new Set(rows.map((operation) => operation.action.id));
  const targetOf = new Map<string, string>();
  for (const operation of rows) {
    const target = retractionTarget(operation);
    if (target !== undefined && target !== operation.action.id && present.has(target)) {
      targetOf.set(operation.action.id, target);
    }
  }
  for (const id of onCycles(targetOf)) {
    targetOf.delete(id);
  }

  const pending = new Map<string, number>();
  for (const target of targetOf.values()) {
    pending.set(target, (pending.get(target) ?? 0) + 1);
  }
  const retracted = new Set<string>();
  const ready = [...present].filter((id) => !pending.has(id));
  while (ready.length > 0) {
    const id = ready.pop()!;
    const target = targetOf.get(id);
    if (target === undefined) continue;
    if (!retracted.has(id)) retracted.add(target);
    const left = pending.get(target)! - 1;
    pending.set(target, left);
    if (left === 0) ready.push(target);
  }
  return retracted;
}

export function appliedOperations(stream: readonly Operation[]): Operation[] {
  const rows = positionalOperations(stream);
  const retracted = retractedActionIds(rows);
  return rows.filter(
    (operation) =>
      !retracted.has(operation.action.id) &&
      operation.action.type !== "RETRACT" &&
      !isDenied(operation),
  );
}

export type ReducerFor = (operation: Operation) => StateReducer;

export function reduceOne(document: PHDocument, operation: Operation, reducerFor: ReducerFor): PHDocument;

export function deriveScope(
  document: PHDocument,
  stream: readonly Operation[],
  reducerFor: ReducerFor,
): { document: PHDocument; applied: ReadonlySet<string> };
```

An action is live if and only if no live retraction names it, so liveness
depends on the set of rows, not their order. `onCycles` returns the ids on a
cycle of `targetOf`. A retraction whose target is absent does nothing until
the target arrives; a retraction on a cycle does nothing. A row's liveness is
settled once every retraction naming it is settled, which the work list
follows without recursion.

`reduceOne` applies one row's action to the scope state: a base action
through the base action reducer, any other through the `StateReducer` for the
row's module version. It never enters `baseReducer`'s rebuild branch.
`deriveScope` starts from `document.initialState`, runs `reduceOne` over
`appliedOperations`, and returns the ids whose call did not throw as
`applied`; a row that throws applies nothing. `reducerFor` resolves the
model's state reducer by module version, which `baseReducer` holds as its
custom reducer.

A stored `error` is diagnostic in base-reducer 3. Derivation never reads it
and never writes it into rows other than the one being appended.

### Undo and redo resolution

```ts
export function undoTarget(stream: readonly Operation[], applied: ReadonlySet<string>): string | undefined {
  const rows = positionalOperations(stream);
  for (let i = rows.length - 1; i >= 0; i--) {
    const operation = rows[i];
    if (applied.has(operation.action.id) && isContent(operation)) return operation.action.id;
  }
  return undefined;
}

export function redoTarget(stream: readonly Operation[], applied: ReadonlySet<string>): string | undefined {
  const rows = positionalOperations(stream);
  const retracted = retractedActionIds(rows);
  const byId = new Map(rows.map((operation) => [operation.action.id, operation]));
  for (let i = rows.length - 1; i >= 0; i--) {
    const operation = rows[i];
    if (retracted.has(operation.action.id)) continue;
    const target = retractionTarget(operation);
    if (target === undefined) {
      if (applied.has(operation.action.id) && isContent(operation)) return undefined;
      continue;
    }
    if (isContent(byId.get(target))) return operation.action.id;
  }
  return undefined;
}
```

`isContent` holds for a row that is not a RETRACT or a NOOP and is not
denied. UNDO retracts the last applied content row. REDO retracts the last
live retraction whose target is content, unless applied content follows it.
`applied` comes from `deriveScope`.

```
a b                 UNDO -> RETRACT(b)      applied: a
a b R(b)            UNDO -> RETRACT(a)      applied: -
a b R(b) R(a)       REDO -> RETRACT(R(a))   applied: a
a b R(b) R(a) R'    REDO -> RETRACT(R(b))   applied: a b
a b R(b) c          REDO refused: c follows the undo
```

```ts
case 3: {
  if (action.input.count !== 1) {
    throw new Error(`${action.type} on base-reducer 3 takes count 1`);
  }
  const operations = document.operations[action.scope] ?? [];
  const { applied } = deriveScope(document, operations, reducerFor);
  const target = action.type === "UNDO" ? undoTarget(operations, applied) : redoTarget(operations, applied);
  if (target === undefined) {
    throw new Error(`Cannot ${action.type === "UNDO" ? "undo" : "redo"}: nothing to ${action.type.toLowerCase()} in scope history`);
  }
  return { document, action: retract(target, action.scope), skip: 0, reuseLastOperationIndex: false };
}
```

Both throws are the reducer's plain errors, as on base-reducer 2. The job
fails, and `JobRollbackSignal` rolls back every write of the job, including
earlier actions of a multi-action job.

After `baseReducer` appends a row, base-reducer 3 re-derives the scope when
the row rewinds, retracts, or is named by a retraction, and otherwise applies
the one row. The executor passes `targeted` from `findRetractionsOf`; a
caller without it, such as a standalone dispatch, computes it from the
document's operations.

```ts
const operations = next.operations[scope];
const targeted = options.targeted ?? retractedActionIds(positionalOperations(operations));
const rebuild = skip > 0 || action.type === "RETRACT" || targeted.has(action.id);
next = rebuild ? deriveScope(next, operations, reducerFor).document : reduceOne(next, operations.at(-1)!, reducerFor);
```

`processSkipOperation`, `garbageCollectV2`, `mapSkippedOperationsV2`,
`undoOperationV2` and the clipboard are not used on base-reducer 3.

### Where the rule applies

On base-reducer 3 every bulk path derives a scope with one `deriveScope` call
instead of calling the reducer per row. The per-row reducer serves appends
only.

`prepareRegularWrite` invalidates the write cache, forcing a full-history
rebuild, when `isUndoRedo(action) || skip > 0`; on base-reducer 3 it does so
when `needsFullHistory` holds.

```ts
function needsFullHistory(write: PendingWrite, targeted: ReadonlySet<string>): boolean {
  return (
    write.skip > 0 ||
    isUndoRedo(write.action) ||
    write.action.type === "RETRACT" ||
    targeted.has(write.action.id)
  );
}
```

| Consumer | Base-reducer 3 |
|---|---|
| `baseReducer` | as above |
| executor, `prepareRegularWrite` | full history when `needsFullHistory`; the reducer does the rest |
| `canBatch` | a RETRACT is never batched |
| write cache cold rebuild at head | one `deriveScope` |
| write cache keyframe and warm rebuilds | one `deriveScope` from the keyframe; the whole log when a row after the keyframe has skip > 0, is a RETRACT, or is named by a retraction |
| read-model sweeps and boot replay through `writeCache.getState` at a revision | `deriveScope` over the stream up to that revision |
| `selectLoadWrites`, `executeLoadJob` | `positionalOperations` only; see Load path |
| `positionByTimestamp`, `reevaluateDocument`, `firstOutOfOrderPair` | `positionalOperations`, unchanged; RETRACT rows move as rows |
| `walkByPosition`, the auth decision model's evaluated-scope apply | `positionalOperations`; re-derive on a RETRACT or a retracted row; never read `error` |
| `replayDocument`, `replayDocumentVersioned`, `baseLoadFromInput`, `baseLoadFromInputVersioned` | `positionalOperations`, then one `deriveScope`; `ignoreSkipOperations` has no effect; PURGE_DOCUMENT applies as a deletion |
| UNDO/REDO preconditions | `undoTarget`, `redoTarget` |
| workflow `effectiveOperations` | `appliedOperations`; one UNDO per retracted target |
| reactor-browser `unsupportedBatchActions` | RETRACT joins; `predictionProtocolVersion` stays 2, since no batched action depends on the version |

```ts
interface IOperationStore {
  findRetractionsOf(documentId: string, scope: string, branch: string, actionIds: string[], signal?: AbortSignal): Promise<Set<string>>;
}
```

`findRetractionsOf` returns the ids among `actionIds` that a stored RETRACT
names, in the shape of `findOperationIds`; `HypercoreOperationStore`
implements it too. It has no revision bound, so a historical rebuild can take
the whole-log path when only a later RETRACT names a row, which costs time
and never changes the result. In a job it reads inside the job transaction,
and the queue runs one job per document at a time. Write cache reads outside
a job follow the existing rule that a read an invalidation overtook is not
cached, and a RETRACT committed after the read lands after the keyframe.

reactor-drive's `NodeProcessor` ignores UNDO, so a retracted ADD_FOLDER stays
in its `DriveNode` rows; RETRACT behaves the same. This is out of scope.

### Load path

In base-reducer 3 a skip is never an undo, so a reshuffle reasons about
positions only.

```
selectLoadWrites, base-reducer 3
  supersededBy           unchanged: positional coverage
  undoneActionIds        not built; a row covered only by a rewind is re-applied
  incomingOpsToApply     unchanged: dedup by action id within the conflict window

executeLoadJob, base-reducer 3
  trivial append         every row written with skip 0
  reshuffle              reshuffleByTimestamp: skipCount on the first row, 0 on the rest
  NOOP skip restoration  not applied
  source row             passed as replayOptions.operation without hash or skip
```

Echo suppression by `sourceRemote` is unchanged. An incoming row's `error` is
not stored, as today.

The reducer hashes the receiver's derived state and never reuses the sender's
`hash`. Only the last row's hash equals the scope's current state; an
earlier row's hash records the state when that row was appended. Write cache
rebuilds replay the replica's own rows and reuse their stored hashes, and a
replay with `checkHashes: false` compares the derived state with the last
stored row, which is the replica's own.

### Signing and replay protection

```
RETRACT signature v2 preimage
  ["v2", documentId, branch, scope, "RETRACT", id, timestampUtcMs, { target }, user.address, user.networkId, user.chainId, app.key]
```

- The signature covers the target, and the preimage binds document, branch
  and scope, so a RETRACT cannot move to another stream and its target is
  looked up only in its own.
- A submitted RETRACT is stored under the author's signature. A submitted
  UNDO or REDO is resolved by the reducer and signed by the reactor through
  `signSynthesized` under `synthesizedActionId(submitted.id)`, as the NOOP is
  today.
- Replay: `DUPLICATE_ACTION` refuses any action id already in the stream,
  including a retracted one and every RETRACT. Retraction is by action id, so
  a re-delivered or re-appended copy of a retracted action stays retracted.
- Revival happens only through a live RETRACT naming the retraction. REDO is
  therefore a new, signed action.

```
execute
  RETRACT, scope "auth" or "document"        ReservedActionError, at the mutation check
  RETRACT, base-reducer 1 or 2               ReservedActionError, in prepareRegularWrite
  RETRACT, target absent from the stream     RetractionRefusedError, "target-missing"
  RETRACT, target already retracted          RetractionRefusedError, "target-retracted"

load
  RETRACT, base-reducer 1 or 2               admitted as an inert row
  RETRACT, scope "auth" or "document"        admitted as an inert row
  RETRACT, target absent                     admitted; does nothing until the target arrives
  RETRACT, target already retracted          admitted
```

The scope refusal joins the purge-marker check at the start of
`executeInScope`, which runs before the document is read. The version refusal
sits in `prepareRegularWrite`, where the header is known.
`RetractionRefusedError` (`documentId`, `target`, `reason`) is execute-only
and joins the terminal allow-list in `JobResultHandler`; it never reaches a
sync path.

### Erasure

A purge deletes every row, and the index entries with them. The purge
marker is in the document scope, where the rule does not run. A RETRACT that
arrives after the purge is refused with `DocumentPurgedError` and dropped,
like any operation. A purged document's versions are `{ "document-purge": 1 }`,
so every base-reducer dispatch sits behind the existing marker checks
(`isPurgeMarker`, `executePurge`).

### Auth scope and decisions

- The monotonic auth stream is never reshuffled and holds no live
  retraction; a RETRACT there is inert, and execute refuses one.
- Decisions see RETRACT as an operation type; a policy grants or refuses it
  like any other, and cannot condition on who wrote the target.
- `positionalOperations`, which is `garbageCollect`, is exact for the
  decision walk, DCB append conditions and re-evaluation, because only
  reshuffles write a skip.

## Backward compatibility and mixed versions

| Document | Writer | Reader | Behaviour |
|---|---|---|---|
| 1 or 2 | any | any | Unchanged, including the pinned defects. |
| 1 or 2 | RETRACT from any peer | any | Stored as an inert row on every replica. A reactor from stage 1 on refuses one submitted locally. |
| 3 | `undoV3` on | `undoV3` on | Base-reducer 3. |
| 3 | `undoV3` on | `undoV3` off, or without agreement | Not sent: the reader does not announce 3, or announces nothing and gets the baseline, and the gate holds the document. The hold releases with a whole-document backfill when the reader announces 3. |
| 3 | any | an older reactor behind a relay | Held at the relay until that reactor announces 3. |
| 3 | any | announces 3 but refuses it | Refused `UNSUPPORTED_PROTOCOL`, non-quarantining; the sender turns the refusal into a hold. |
| 3 | `.phd` import | agreement, `undoV3` off | CREATE refused with `UnsupportedProtocolVersionError`. |
| 3 | `.phd` import | without agreement | Not prevented: the build reads version 3 as `>= 2` and runs base-reducer 2. |

Receipt judges every row, not only CREATE: a write from a peer that does not
announce the document's version is refused `PEER_PROTOCOL_UNSUPPORTED`.

Rolling back:

- Turning `undoV3` off over a store that holds base-reducer 3 documents
  refuses to start with `UnsupportedStoredProtocolError`, unless the host
  builds with `withUnsupportedStoredDocuments("read-only")`, which keeps those
  documents read-only.
- Under `migrationStrategy: "auto"`, a build below stage 3 refuses to start
  over a store that ran `027_index_operation_retracts`, because its migrator
  finds an executed migration it does not know. Once stage 3 runs, it is the
  floor for binary rollback.

An existing document opts in by copy. `protocolVersions` is immutable after
CREATE and part of the derived id, so there is no in-place switch. The copy
path is DriveClient's, which seeds the new document from the source's state
(`initialState: srcDoc.state`, no operations); it sets
`protocolVersions["base-reducer"] = 3` on the source it passes to
`createCopyHeader`, which otherwise keeps the source's versions. History
before the copy is not undoable. `ReactorDriveClient.copyNode` and
reactor-browser's duplicate replay the source's operations under the copy
header, so they keep the source's version.

## Stages

One PR per stage, merged in order; Parallel execution lays out the work
inside each. Stages 1 to 6 ship with `undoV3` off. Every stage leaves
base-reducer 1 and 2 unchanged. Tests enable the flag where they need it.

A "v3 twin" is a pinned undo scenario on a base-reducer 3 document in the
same file, with a peer's undo expressed as `retract(target)`. The v2
original of an undo defect is pinned to base-reducer 2 explicitly, keeps
`it.fails`, and is labelled as base-reducer 2 behaviour. The (ii) twin is a
new test in `effective-ops-rules.test.ts` (ii) in which UNDO, REDO, UNDO
succeeds on base-reducer 3. Each stage's twins are listed in Pinned test
accounting.

1. **Version gate.** `undoV3` declared, off, and read by the `base-reducer`
   capability entry. `baseReducerVersion` narrows to `BaseReducerVersion`,
   accepting 1 and 2. Explicit version dispatch at the four sites. RETRACT
   refused on execute; on load it stays an inert row. RETRACT reserved, and the
   codegen check. The pinned v2 tests pin base-reducer 2 through
   `createCreateDocumentOperation` and `createPresignedHeader`.
   Twins: none.
2. **Shared rule and reducer.** `positionalOperations`, `retractedActionIds`,
   `appliedOperations`, `reduceOne`, `deriveScope`, `undoTarget`,
   `redoTarget`, `retract` and its schema; the base-reducer 3 branches; the
   replay paths. `baseReducerVersion` accepts 3. The reactor still refuses a
   version 3 document without `undoV3`. Unit tests and the model-level
   property test.
   Twins: none.
3. **Execute path and retraction index.** `027_index_operation_retracts`,
   `findRetractionsOf`, `needsFullHistory`, `targeted`, `canBatch`, RETRACT
   admission and `RetractionRefusedError`, UNDO/REDO synthesized as RETRACT,
   and the write cache and read-model rebuilds.
   Twins: the stage 3 rows.
4. **Load path.** Receiver-derived skips, no NOOP skip restoration, no
   `undoneActionIds`, receiver-local hashes.
   Twins: the stage 4 rows.
5. **Decisions.** `walkByPosition` and the auth decision model's
   evaluated-scope apply re-derive on a RETRACT or a retracted row and stop
   reading `error`. Tests for `positionByTimestamp` and `reevaluateDocument`
   moving RETRACT rows.
   Twins: the stage 5 row.
6. **Client.** New `IReactorClient.undo` and `redo`. On base-reducer 3
   `ReactorClient` takes the stream from `getOperations`, `applied` from
   `deriveScope` with the model from `getDocumentModelModule`, resolves the
   target, and submits a signed RETRACT; on 1 and 2 it submits UNDO and
   REDO. reactor-browser adds RETRACT to `unsupportedBatchActions` and
   exposes undo and redo availability; workflow's `effectiveOperations` gains
   its base-reducer 3 branch; academy docs describe base-reducer 3.
   Twins: none.
7. **Default on.** `undoV3` defaults on, so the capability announces and
   prefers 3 and existing selection picks it where members agree. A
   parentless create through the client takes the local preference, 3. A
   header built with no versions still defaults to 2. DriveClient's copy
   takes a `protocolVersions` override for copy-to-v3.
   Twins: none.

### Separate track: re-sending lost operations

Loss is not specific to undo. It follows from damaged stores, v2 documents,
and any future defect, and base-reducer 3 removes only the undo-driven cause.
We run it as a parallel track with its own plan, announced as agreement's
`sync.anti-entropy` feature, and name only its scope and tests here.

- **R1, anti-entropy.** On connect and with acks, peers exchange a
  per-stream digest of the ids `positionalOperations` keeps, at or below
  `settledThrough`. On a mismatch the peer sends those rows, bypassing
  `excludeSourceRemote` and `sinceTimestampUtcMs`; the receiver dedups.
- **R2, fresh channels.** `sinceTimestampUtcMs` becomes a hint confirmed by
  an R1 digest exchange before a fresh channel trusts it.

from the stage branch, and each file has one owner. A stage that adds shared

### Conventions for implementing agents

- `pnpm` only; `pnpm tsc --build`, never a global `tsc`. The oxlint and
  oxfmt pre-commit hook may rewrite staged files; re-stage only your paths.
- Rebuild `packages/shared` (`pnpm build`, a tsx bundle, not `tsc`) and
  `packages/reactor` dists before downstream tests. In reactor-browser run
  `pnpm test`; `vitest run <file>` passes falsely in its browser project.
- Never edit a generated file by hand; run codegen or the schema emitter.
- A terminal error joins `JobResultHandler`'s allow-list, or the job retries.
- A v3 twin is a new test, never an edit of its v2 original. An original a
  twin fixes keeps `it.fails`; only the accounting's R1 and R2 rows flip, in
  the resend track.
- Comments rare and terse. Reducers apply operations and derive state; never
  describe them as folding.
- Commit per logical change with a body that says why. Never amend, rebase,
  force-push or push.
- A red test stays red until its cause is fixed. No retries.
- Record every deviation in the PR body with the reason. Do not edit this
  plan to match the code.

## Migration

- Schema: `027_index_operation_retracts`, registered in the migrator, creates
  `idx_operation_retracts` on `Operation` only, in Postgres and PGlite. The
  target expression carries its own parentheses inside the `sql` fragment,
  since Kysely's `.expression()` adds none, and queries name the type as the
  literal `'RETRACT'` so generic plans can use the partial index. No
  backfill: no stored row is a RETRACT before stage 3.
- Documents: none. Base-reducer 1 and 2 documents keep their rule and their
  stored rows. Opting in is a copy.

## Test strategy

- **Unit, shared.** `retractedActionIds` over chains, redo of redo, cycles,
  self-targets, absent targets, and two retractions of one target.
  `undoTarget`/`redoTarget` against the stack table above, including a REDO
  whose target throws.
- **Twins.** Each pinned scenario on base-reducer 3, as listed in the
  accounting.
- **One-rule agreement.** For every stream a twin produces: served state,
  cold rebuild, keyframe and historical rebuild, `replayDocument` with
  `checkHashes: false`, and a `.phd` round trip all equal `deriveScope`, and
  no row carries an error from applying an action twice. A long stream
  rebuilds in time linear in its rows.
- **Differential property test, model level.** Replicas as row lists; random
  execute, UNDO, REDO, RETRACT, partial and repeated delivery, and skewed
  timestamps; quiesce by full exchange. Local writes are positioned by
  timestamp, as `positionByTimestamp` does. Asserts equal live sets and equal
  order across replicas.
- **Differential property test, reactor level.** The same generator at small
  bounds against in-process reactors connected by the test channel, seeded,
  printing the seed on failure.
- **Mixed fleets.** The `withPeerCapabilities` fleet harness with `undoV3` on
  and off: holds, releases with backfill, and a RETRACT into a base-reducer 2
  document stored inert on every replica.
- **v2 regression.** The whole existing suite unchanged, plus a corpus of the
  pinned v2 streams with their served states, asserted equal before and after
  every stage.

## Decisions

1. **Per-document version plus an op type.** The document version selects one
   rule for the whole stream, so no stream mixes positional undo with
   retraction. The RETRACT type makes the stored intent self-describing. A
   per-op marker alone would leave v2 NOOP semantics live inside new streams.
   A field on the NOOP is rejected because base-reducer 2 restores skip 1 on
   a re-appended incoming NOOP and would turn it into a positional undo.
2. **`base-reducer`, not a new key.** The base-reducer version already
   selects the undo implementation. A separate `undo` key would behave the
   same on older reactors and add a second dispatch.
3. **Target by action id.** The operation id is derived from the action id
   within a stream, so they are equivalent in-stream. The action id is what
   the signer names and survives a branch merge.
4. **Set-based liveness.** Retraction depends on which rows are present, not
   their order, so reshuffles, clock skew and delivery order cannot change
   what is retracted. Cycles need forged ids and are made inert
   deterministically.
5. **Skip is positional and receiver-derived.** A receiver's skip describes
   its own rewind, and a trivial append rewinds nothing. Computing every skip
   from the receiver's log removes defects 1 and 2 at their source and lets a
   reshuffle ignore undo entirely.
6. **REDO retracts a retraction.** No clipboard or derived stack is stored;
   the redo stack is read from the stream. Applied content after an undo ends
   the redo chain, matching base-reducer 1. UNDO needs the applied set,
   because a row that throws applies nothing; REDO's target test is
   syntactic, because its target is retracted and never applied.
7. **UNDO and REDO remain.** They resolve to RETRACT in the reducer, as
   base-reducer 2 resolves UNDO to a NOOP, keeping `undo()` callers and the
   synthesize-and-sign path working. RETRACT is the first-class form, and the
   client submits it so the author's signature covers the target.
8. **Absent targets.** Refused on execute, where the author must see the
   target. Admitted on load, where delivery order is arbitrary; the set-based
   rule makes them effective when the target arrives.
9. **Base-reducer 2 frozen, including trivial-append skips.** We do not
   change its derivation or its write paths. Zeroing the sender's skip on v2
   non-NOOP rows fixes the v2 backdated-write case, but any v2 change makes
   old and new reactors write different rows for the same input during
   rollout. The defects stay pinned as v2 behaviour.
10. **Peer protocol agreement, not rollout order.** A reactor without
    base-reducer 3 would read a version 3 document as base-reducer 2 and
    write positional NOOPs into it. As a version of a peer capability,
    base-reducer 3 is selected only where every member supports it and held
    from every peer that does not, at every hop, so releases need no
    coordination and undo adds no sync code.
11. **The capability entry changes in place; shared only narrows.** Support
    is read through `localSupports`, so no consumer needs the entry by name.
    Support gating stays in the reactor, where
    `UnsupportedProtocolVersionError` lives.
12. **An expression index, not a column.** The executor must know whether a
    row it is about to write is retracted without reading the whole stream.
    An index over the action JSON needs no write-path change and no backfill,
    and follows the existing protocol-versions index on `Operation`. A
    derived set in the write cache would need to survive keyframes.
13. **Hashes are receiver-local.** Set-based liveness lets a receiver's
    state at a row differ from the sender's, for example while a
    retraction's target has not arrived, so a reused sender hash would fail
    a hash-checking replay with `HashMismatchError`. The signature does not
    cover the hash, and nothing compares hashes across peers.
14. **Stored `error` is diagnostic.** A retraction can make an earlier failure
    succeed or a later success fail. Re-deriving keeps replicas that received
    rows in different orders equal.
15. **A RETRACT outside the rule is inert on load and refused on execute.**
    Reactors before stage 1 store any action type, so ordinary clients can
    put a RETRACT into a base-reducer 1 or 2 document or the auth scope.
    Refusing it on load would quarantine the document on every upgraded
    reactor and dead-letter the batch's legitimate rows; storing it inert is
    what older readers do, so replicas keep identical rows. Target refusals
    are deterministic, so `RetractionRefusedError` is terminal and, being
    execute-only, needs no sync classification. Count and "nothing to undo"
    stay the reducer's plain errors because shared cannot raise reactor
    errors.
16. **Bulk paths derive once.** A retracted-set check per row would make
    rebuilds and replay quadratic in the stream. One `deriveScope` keeps them
    linear, and `reduceOne` never entering the rebuild branch keeps
    `deriveScope` from re-entering itself.
17. **Erasure needs nothing of its own.** The index lives on `Operation`
    rows, which a purge deletes, and the marker lives in a scope where the
    rule does not run. Keeping the dispatch behind the marker checks avoids
    giving a purged document a base-reducer version it does not have.
18. **Resend is a separate track.** It is protocol-independent and needed for
    v2 documents and damaged stores whatever this plan does.
19. **Opt-in by a copy seeded from state, through DriveClient.** An in-place
    switch would contradict CREATE-fixed `protocolVersions` and the derived
    id, and a reshuffle could move rows across the switch. Replaying the
    source's history would replay v2 rows under v3 rules, or attribute every
    copied operation to the copier; seeding from state costs undo past the
    copy.
20. **UNDO stays scope-wide.** It retracts the last applied operation by
    anyone, as today. Per-signer undo needs no protocol change later: a
    client can already submit a RETRACT naming its own last operation.
21. **No target-author condition yet.** A policy grants or refuses RETRACT as
    an operation type. Letting a policy compare the target's signer with the
    retractor needs the decision model to read the target, and is a
    follow-up.
22. **`RETRACT` is reserved, and codegen checks reserved names.** A model
    operation named RETRACT would be read as the base action on
    base-reducer 3. The editor's validation does not cover specs written
    elsewhere.
23. **A foundation per stage, not one up front.** One foundation carrying
    every later signature would ship stubs in stage 1's PR and move migration
    027, and with it the rollback floor, to stage 1. Per-stage foundations on
    stacked branches give later tracks the same stable signatures, from 2a
    and 3a, while every PR ships complete.
