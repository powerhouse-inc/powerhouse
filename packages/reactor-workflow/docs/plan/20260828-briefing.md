# Requirements Analysis for the new Powerhouse Workflow Automation Feature

## Background

Powerhouse is a software development and consultancy group that produces an open-source framework for local-first, 
distributed apps, agents, and platforms with a data primitive at its core which is the Powerhouse document model.

This folder contains various git repositories that comprise the full range of the framework layers: 

* The `powerhouse` repository contains the core components of the docment model framework, most notably: 
  * The Reactor core component, a TypeScript library for processing, storing and synchronizing document actions and operations
  * The dynamic loaders that can load Reactor (TS) packages with specific document models, document editors, and processors
  * The ph-cmd/ph-cli tools and code generators for scaffolding new Reactor packages, installing them, etc. with Vetra Studio, its development UI
  * The Renown component, used for authenticating users and signing document operations with a cryptographic key
  * The Switchboard app, a GraphQL and MCP webservice that acts as a host application for the Reactor and its packages
  * The Connect app, a React-based web app, that similarly acts a host application for the Reactor and its packages
  * The Verdaccio registry, used to distribute Reactor packages to the host applications for installation.

* The `recipes` repository, a treasure trove of usage patterns for the Powerhouse Reactor and document models framework. 

* The `ph-clint` repository contains the Powerhouse AI agent framework, which integrates the Mastra agent framework with the Powerhouse 
    Reactor and document models. It offers an agent harness builder to create agent CLIs and web interfaces that use the Reactor and 
    Powerhouse documents as their app and data infrastructure.

* The `vetra-cli`, a ph-clint implementation project for the Vetra Agent, an app builder interface for building Powerhouse-based 
    apps and platforms with agentic support. 

* The `win-test` repository, a recent prototype of a Powerhouse desktop application that offers Connect and Switchboard through a simple installer.
    Users can then install Reactor packages and use the various document editors and drive apps that are included. This repository uses Tauri.

* The `pfnur-toll-collect-portal` a monorepo with a project built for a Powerhouse client. It is a typical platform use case and it contains an 
    intelligent document processing flow for scanning PDF toll statements issued to Road Transport Operators using German highways.

## Feature Description

The new workflow automation feature will extend the Powerhouse software with a standardized way of: 

* Defining and setting up triggers that will initialize a new, worker-based workflow running besides a Reactor. 
  Triggers will include: timers, webhooks exposed through Switchboard, user buttons in Connect, etc.

* Defining and setting up additional workflow blocks such as logic operators, actions and agent-decision blocks.

* Implementing and distributing a new Reactor package module type (next to document models, editors, processors, etc), 
  called `connectors`, that will integrate an external service or API with Reactor workflows: 

    * Input: pushing and polling trigger implementations that may fire when, for example, a new e-mail arrives, a file was added or changed, 
      a Discord message was sent, a paperless webhook triggers, etc. 

    * Output: action block implementations that send a new e-mail, create or update a file, send a Discord message, etc.

The feature will be a new, first-class mechanism that optimally leverages, reuses, and complements existing mechanisms in the framework. It 
will also take inspiration from and generalize a number of mechanism that were implemented in a custom way for existing client projects. For example: 

* Workflow configuration will happen at runtime as a Powerhouse workflow document. The framework will then instantiate the triggers and start the 
  workflow logic when one fires. 

* Connector types, trigger types, logic operator types, agent decision types, etc., will be dynamically loaded at runtime by Reactor host applications, 
  in the same way that document models are dynamically loaded from Reactor packages. So developers can provide new workflow blocks to their users.

* Connector/triggers and workflow will run in workers, reusing the worker pattern in the `pfnur-toll-collect-portal` and the existing RPC mechanism for 
  calling the Reactor, attachment service, etc.

* Implementation will follow existing Reactor processor patterns and the current processor implementation may be improved for maximum synergies.

* The `ph-clint` functionality will be integrated two-ways by enhancing agents with workflows, and by enhancing workflows with agent calling capabilities.

* The ph-cmd/ph-cli and Vetra Studio+CLI features will be extended to facilitate workflow definition, scaffolding and implementation.

* Intelligent Document Processing blocks will be implemented as a first test for the new workflows. This dynamic workflow configuration should be largely at 
  feature-parity with the document processing flow used for PFNUR. 

* The goal is to ultimately enable an "if-this-then-that" experience for end-users of the desktop application, where they can tell an agent: "When I receive an e-mail, 
  check if it's a new invoice, add it to my billing app drive, and send me a notification on Discord."
