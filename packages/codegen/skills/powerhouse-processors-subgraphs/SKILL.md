# Processors and subgraphs

A processor is a `powerhouse/processor` document in the Vetra drive; a subgraph is a `powerhouse/subgraph` document. Codegen writes the scaffold once the document is CONFIRMED. Create both through `reactor-mcp`; `ph generate processor` and `ph generate subgraph` are for repairing existing folders (see "The CLI"). Never write the scaffold by hand.

- Processor: receives the operations of documents of the types it subscribes to, in every drive, and derives data from them: rows in relational tables, or analytics series. It runs in Switchboard, in Connect, or both.
- Subgraph: a GraphQL schema and resolvers that Switchboard serves at `/graphql/<id>` and in the supergraph at `/graphql`. Every document model already has a subgraph of its own; write one for queries and mutations beyond those, such as reading a processor's tables.

## Create a processor

1. Check `processors/` for a processor with the same purpose. If one exists, ask in an interactive session whether to change it or create another.
2. `getDocumentModelSchema` with `type: "powerhouse/processor"`.
3. `createDocument` with `documentType: "powerhouse/processor"` and `driveId` set to the `vetra-<hash>` drive.
4. One `addActions` call, scope `global`:
   - `SET_PROCESSOR_NAME` (`{ name }`). The folder and id are the kebab-cased name.
   - `SET_PROCESSOR_TYPE` (`{ type }`): `"relational"` or `"analytics"`. Any other value is rejected with `UnsupportedProcessorTypeError`.
   - `ADD_DOCUMENT_TYPE` (`{ id, documentType }`) per document type, e.g. `{ "id": "invoice", "documentType": "acme/invoice" }`. `id` is an entry id you choose, unique in the document.
   - `ADD_PROCESSOR_APP` (`{ processorApp }`) per app: `"switchboard"`, `"connect"`, or one of each. Other values are rejected.
   - `SET_PROCESSOR_STATUS` with `{ status: "CONFIRMED" }`.
5. Codegen runs only when the document has a name, a type, at least one document type, at least one app, and status CONFIRMED. Call `getCodegenStatus` with the processor document's `documentId` and `waitSeconds: 60`. It reports `waiting-for-install` while Vetra adds the processor's dependencies (up to a minute); once it is `done`, the processor is in `processors/<id>/` and registered in `processors/switchboard.ts` or `processors/connect.ts`.
6. Implement the processor. See [references/processors.md](references/processors.md).

`REMOVE_DOCUMENT_TYPE` (`{ id }`) and `REMOVE_PROCESSOR_APP` (`{ processorApp }`) undo the two list actions.

Choose the type:

- `relational`: tables you define, one namespace per drive. Every drive's instance receives the operations of every drive, so each namespace holds rows for the documents of all drives; a query by `driveId` alone does not scope to that drive. Use it for read models: lists, indexes, lookups across documents. A subgraph or an editor queries them.
- `analytics`: numeric series by metric and dimension in the analytics store, queried through the core `analytics` subgraph. Use it for totals and time series.

Choose the apps:

- `switchboard`: runs in the Switchboard server. Pick it when a subgraph serves the data.
- `connect`: runs in each Connect user's browser. Pick it when an editor reads the data in Connect.

## What codegen writes for a processor

Every file under `processors/<id>/` is written once, when missing. Codegen never rewrites an existing one.

| Path | Owner |
| --- | --- |
| `processors/<id>/processor.ts` | You. The class and its `onOperations`. |
| `processors/<id>/factory.ts` | You. Builds the processor for each drive and sets its `filter`. |
| `processors/<id>/migrations.ts`, `schema.ts` | You (relational only). The tables, and their types. |
| `processors/<id>/index.ts` | Codegen. Re-exports `factory.js` and `processor.js`. Don't edit. |
| `processors/connect.ts`, `processors/switchboard.ts` | Codegen. It adds an import and a `processorFactoryBuilders` entry for each app the processor runs in. It never removes one. |
| `processors/factory.ts`, `processors/index.ts` | Codegen. `ph migrate` overwrites them. |
| `powerhouse.manifest.json` (`processors`) | Codegen. |

`ph migrate` and `ph generate all` regenerate every processor folder, which writes only missing files and re-registers the processor. They read the processor back from its files: the apps from `connect.ts` and `switchboard.ts`, the type from the imports of `processor.ts` (`RelationalDbProcessor` or `IAnalyticsStore`), the document types from the `documentType` array in `factory.ts`. Keep those intact.

A folder in `processors/` with files but no `processor.ts`, where no file imports `./processor`, is hand-written: codegen leaves it, its registrations and its manifest entry alone. A folder without a processor's shape at all, such as shared helpers, is also left alone, with a warning.

## Change a processor

The document drives the first scaffold. Later changes to it reach the code only in part:

- Document types: edit the `filter` in `processors/<id>/factory.ts`. `ADD_DOCUMENT_TYPE` does not change an existing factory.
- Apps: `ADD_PROCESSOR_APP` registers the processor in the new app's file. `REMOVE_PROCESSOR_APP` does not unregister it; delete its import and array entry in `processors/<app>.ts`.
- Name: a new name scaffolds a second folder. Delete the old folder and its entries in `processors/connect.ts` and `processors/switchboard.ts`.
- Type: fixed once scaffolded. To switch, delete the folder and its entries, then send `SET_PROCESSOR_TYPE`; any action on a confirmed document runs codegen again.

Keep the document in step with the code, so the Vetra drive describes what the package ships.

## Create a subgraph

1. Choose a name the server does not serve already. Codegen refuses, and writes nothing for, a name whose kebab case is:
   - a core subgraph: `analytics`, `system`, `r`, `inspection`, `inspection-admin`, `auth`;
   - a document model's subgraph: the model's kebab-cased name, e.g. `invoice` in a project with an `Invoice` model. Use `invoice-api` instead.
2. `getDocumentModelSchema` with `type: "powerhouse/subgraph"`.
3. `createDocument` with `documentType: "powerhouse/subgraph"` and `driveId` set to the `vetra-<hash>` drive.
4. One `addActions` call, scope `global`:
   - `SET_SUBGRAPH_NAME` (`{ name }`). The folder, id and route are the kebab-cased name.
   - `SET_SUBGRAPH_STATUS` with `{ status: "CONFIRMED" }`. While DRAFT, codegen writes nothing.
5. Call `getCodegenStatus` with the subgraph document's `documentId` and `waitSeconds: 60`. Once it is `done`, the subgraph is in `subgraphs/<id>/` and exported from `subgraphs/index.ts`; `failed` or `skipped` carries the reason. Vetra retries a job once by itself; to run codegen again, send any action to the confirmed document, such as `SET_SUBGRAPH_STATUS` `CONFIRMED`.
6. Write the schema and resolvers. See [references/subgraphs.md](references/subgraphs.md).

## What codegen writes for a subgraph

Every file under `subgraphs/<id>/` is written once, when missing. Codegen never rewrites an existing one.

| Path | Owner |
| --- | --- |
| `subgraphs/<id>/schema.ts` | You. The `schema`, a `gql` template. |
| `subgraphs/<id>/resolvers.ts` | You. `getResolvers(subgraph)` returns the resolver map. |
| `subgraphs/<id>/lib.ts` | You. Helpers. |
| `subgraphs/<id>/index.ts` | You, with two limits: keep the class extending `BaseSubgraph`, and keep `name` a string literal. Codegen finds the subgraph by them; without them it skips the folder. |
| `subgraphs/index.ts` | Codegen. It adds `export * as <Name>Subgraph from "./<id>/index.js"` for each subgraph class it lacks. |
| `powerhouse.manifest.json` (`subgraphs`) | Codegen. |

`name` in `index.ts` is the route and the name the server checks. Renaming the document scaffolds a second folder; delete the old one and its line in `subgraphs/index.ts`.

## The CLI

The Vetra document is the primary path. Use the CLI on folders that exist:

- `ph generate processor --dir <id>`, `ph generate subgraph --dir <id>`: run codegen again for one folder. It writes missing files, re-registers the module, and adds missing dependencies to `package.json` and installs them. `--all` does every folder. Vetra's codegen does the same when it writes a confirmed processor or subgraph.
- `ph generate migration-file --path processors/<id>/migrations.ts`: writes `processors/<id>/schema.ts`, the table types, from the migration. It overwrites that file.

`ph generate processor --name` and `ph generate subgraph --name` scaffold without a document, which leaves the Vetra drive without one. Don't use them when Vetra is running.

## Check your work

- `npm run tsc`
- `npm run lint:fix`
- `npm run test` for the tests you wrote. A new relational processor gets a starter `processor.test.ts`; adapt it when you change the migration. It uses `@powerhousedao/shared/processors/testing`: `createTestRelationalDb()` (in-memory PGlite), `runProcessorMigrations(db, namespace, up)`, and `operationsWithContext(document)` / `testOperation({...})` to feed `onOperations` with operations from your model's reducer.
- After a subgraph schema change, `ph generate subgraph --dir <id>`. It prints a warning for each type or root field the server would leave out of the supergraph, or a subgraph it would refuse.
