# Registry replica CPU per request under uncached reads (HEAD f6b9ee88c9)

Per-route CPU on one replica, measured the same way as [profile-2026-09-30T15-40.md](profile-2026-09-30T15-40.md) (`2bb2b9f802`), after the artifact, manifest, piece and list-page caches, the uplink 404 cache, and S3 checksums only where required. `f6b9ee88c9` changes only the harness on top of `c632f14cc8`, so the registry code is `c632f14cc8`.

## Method

- **Stack:** `STRESS_COMPOSE_OVERRIDE=docker/compose.profile.yml STRESS_SCENARIOS=reads-uncached STRESS_READ_LEVELS=16 STRESS_STEP_SECONDS=5 STRESS_KEEP_STACK=1 pnpm stress REF=HEAD`, which leaves the 60 seeds published. Replicas have 1 CPU and 1 GiB.
- **Load:** the harness's `load-proc.ts` generators, with `_nocache` on every URL unless noted. Each route alone, then `READ_MIX`, straight at registry-1 with 64 clients. The mix also ran through NGINX with 128 clients. Each run has 5 s of warm-up and a 12 s window.
- **CPU per request:** the container's cgroup `usage_usec` over the window, divided by the requests served. Through NGINX, both replicas' CPU is summed. Postgres' cgroup CPU is reported the same way.
- No CPU profile was taken, so there is no breakdown by area.

## List routes: the page cache and the catalog size

`_nocache` changes `req.originalUrl`, and the page cache is keyed on it (`packages/registry/src/middleware.ts:359`), so the table above measures list routes on a cache miss. Without `_nocache`, every request after the first hits the cache:

| Route           | Busted µs/req | Cached µs/req | Cached req/s |
| --------------- | ------------- | ------------- | ------------ |
| pieces          | 210           | 85            | 11307        |
| packages        | 157           | 42            | 23193        |
| packages-search | 302           | 53            | 18650        |

On a miss, the cost grows with the catalog. After the stress test's publish scenario (2,600 packages) on a fresh stack:

| --------------- | -------------------------------------- | ----------------------------------------- | -------------------- |
| pieces          | 210 / 315                              | 426 / 3,281                               | 608, 102             |
| packages        | 157 / 268                              | 340 / 1,823                               | 1,095, 82            |
| packages-search | 302 / 2,621                            | 1,026 / 59,365                            | 34, 1,897            |
| package-detail  | 115 / 152                              | 110 / 175                                 | 7,395, 6.5           |
| npm-metadata    | 319 / 47                               | 332 / 65                                  | 2,989, 14.9          |
| Mix direct      | 164 / 92                               | 277 / 1,562                               | 1,278, 1.6           |

- With 2,600 packages the mix is bound by Postgres, not the replica: Postgres uses ~2 cores, and registry-1 uses 0.35.
- `EXPLAIN ANALYZE` of one search: a seq scan of `registry_packages` with the `<%`, `@@` and `LIKE` filter, a `count(*) OVER ()` window over every match, and a top-N sort on `ts_rank` and `word_similarity`. It takes 46 ms, or about 18 µs per row. The trigram index isn't used.
- Every probe name is `stress-<run>-<n>` or `stress-seed-<run>-<n>`, so a probe search matches all 2,600 rows. A catalog with varied names matches fewer rows, but the seq scan still computes `word_similarity` for each row.
- In the sampled `pg_stat_activity`, the `LISTED` query (`/packages` and search) was active 3.5× as often as the `/pieces` query. No other query came close.

## Caveats

- **Host load:** the 1-minute load average was 4–8 during the 60-seed runs, and 3–4.5 during the 2,600-package runs. The previous profile reported 5–9. Docker has 18 CPUs and 8 GB.
- **Profiler overhead:** `compose.profile.yml` enables the inspector on registry-1 but no profile ran, which matches the previous profile's "off" column.
- **Windows:** 12 s for every run, including the mix via NGINX, which ran 30 s in the previous profile.
- **npm-metadata:** the stateless stack has no uplink stub. After the first miss, the uplink 404 cache keeps reads off npmjs.
- **Probe packages are tiny:** a 495 B CDN file and a 19.7 KB bundle both fit the 1 MiB artifact cache. Larger artifacts skip it.
