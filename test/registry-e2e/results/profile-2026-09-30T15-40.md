# Registry replica CPU profile under uncached reads (HEAD 2bb2b9f802)

Where one replica's main thread spends its CPU when every read reaches it (`reads-uncached`). The stack is `docker/compose.stress.yml` with `docker/compose.profile.yml`, which opens registry-1's inspector. Seeds are the stress test's 60 probe packages.

## Method

- **Stack:** `STRESS_COMPOSE_OVERRIDE=docker/compose.profile.yml STRESS_SCENARIOS=reads-uncached STRESS_READ_LEVELS=16 STRESS_STEP_SECONDS=5 STRESS_KEEP_STACK=1 pnpm stress REF=HEAD` publishes the seeds and leaves the stack up. Replicas have 1 CPU and 1 GiB, as in the stress test.
- **Load:** the harness's `load-proc.ts` generators with `_nocache` on every URL, 5 s of warm-up and then a measured window.
  - **Mix:** `READ_MIX` through NGINX at 128 clients for 30 s, which is the scenario itself. The same mix also ran straight at registry-1 with 64 clients.
  - **Per route:** each route alone, straight at registry-1 with 64 clients for 12 s. Every route ran twice, once with the profiler off and once with it on.
- **CPU profile:** a CDP client on `127.0.0.1:4939` calls `Profiler.start` (500 µs sampling) just before the measured window and `Profiler.stop` just after it. The profile therefore covers only the load, not boot or seeding.
- **CPU per request:** the container's cgroup `usage_usec` over the window, divided by the requests served. This includes libuv threadpool and GC helper threads. "Main-thread busy" comes from the profile.
- **Attribution:**
  - **Exclusive by area:** each sample goes to the nearest npm package or app frame above its leaf. Bundled plugin code is mapped back to its package through the bundle's `//#region` markers.
  - **Inclusive:** a sample counts once for each area on its stack.
  - A sample made only of Node internals is classed by the HTTP side on its stack.

## Headline

- The mix costs **~0.30 ms of CPU per request** on an otherwise idle host (the per-route costs weighted by `READ_MIX`), which caps a 1-core replica at ~3.3k req/s. With both replicas and NGINX loaded, the same mix measured 0.56 ms/req without the profiler (3,412 req/s over two replicas) and 0.65 ms/req with it (2,928 req/s).
- A two-replica run without NGINX also costs 0.59 ms/req, so NGINX isn't the difference. The rise is host contention, and every area grows by about the same factor (see Caveats).
- **The S3 client is the biggest single cost:** 36% of main-thread CPU in the mix, and about half of every file or bundle read. That is SigV4 signing, the smithy middleware chain, flexible-checksum validation, endpoint resolution and serde.
- **npm metadata is the costliest route (0.79 ms).** Every request for a local package makes an HTTPS round trip to registry.npmjs.org, which answers 404, and also does an S3 GET of `package.json`.
- Postgres-backed routes are cheap on the replica (80–230 µs). Their pg time goes mostly to row parsing of JSONB columns the response doesn't need. Search alone is bound by Postgres, not by the replica: at 773 req/s Postgres runs at its 2-core limit and the replica at 0.28 cores.

## Optimisations, ranked by expected gain on the mix

The estimates below come from the per-route costs, weighted by `READ_MIX`, from a baseline of 30.3 µs-weighted units, which is 0.303 ms/req. None of these changes is implemented here.

### 1. Serve immutable artifacts from an in-memory LRU (~30% of mix CPU)

**Evidence:** cdn-file and piece-bundle are 48% of the mix's CPU. In each, the S3 GET accounts for 47–51% of main-thread time (AWS SDK), plus the http client, the stream plumbing and most of the GC (9–12%). The keys are immutable: `filesKey(pkg, version, file)` and `bundleKey(pkg, version, file)` name a published version, which never changes.

**Change:**

- In `createS3ArtifactStore().get()` (`packages/registry/src/artifacts.ts:76`), or in a wrapper passed as `services.artifacts` (`packages/registry/src/run.ts:320`), keep objects under a size cap (say 1 MiB each, 64–128 MiB in total) as `Buffer`s in a byte-bounded LRU.
- `stream()` (`packages/registry/src/middleware.ts:219`) then answers a hit with `res.end(buf)`.
- Evict `<pkg>/<version>/` keys on the `versions-removed` events the `Catalog` already handles (`packages/registry/src/catalog.ts:147`).

**Expected result:** cdn-file drops from ~270 to ~90 µs and piece-bundle from ~320 to ~120 µs, saving ~9.3 of 30.3. `npm-tarball` could share the cache later through `S3PackageManager.readTarball` (`packages/verdaccio-s3-storage/src/s3PackageManager.ts:219`).

### 2. Stop the npmjs round trip and the S3 manifest read on every local npm-metadata request (6–22% of mix CPU)

**Evidence:**

- npm-metadata costs 785 µs/req, a quarter of the mix. Of that, the `got` uplink accounts for 14.4% (102 µs), plus its share of the http client and HTTPS (8%) and a 404 `ClientError` per request.
- The cause is in verdaccio's `mergeCacheRemoteMetadata`, which returns the local manifest only when `_uplinks.npmjs.fetched` is recent. A package published here never has that field, because npmjs answers 404, so each request fetches again.
- The request is issued because every name matches `'**': { proxy: 'npmjs' }` (`packages/registry/src/verdaccio-config.ts:108`).
- The S3 GET of `package.json` in `readPackage` (`packages/verdaccio-s3-storage/src/s3PackageManager.ts:80`) adds another 25% (176 µs).
- Latency suffers too: p50 is 43 ms at 64 clients, and each read depends on npmjs being reachable.

**Change, minimal:** skip uplinks for packages published here. The simplest hook is `readPackage` (`s3PackageManager.ts:93`). A manifest with `_attachments` or versions recorded in `verdaccio_manifests` is local, so the hook can stamp `_uplinks[<each configured uplink>] = { fetched: Date.now() }` on it before returning it. Verdaccio then short-circuits. This saves ~1.8 of 30.3 (6%) and removes the external dependency.

**Change, fuller:** also cache parsed manifests in the plugin, keyed by name and validated against `verdaccio_manifests.rev` (a primary-key lookup rather than an S3 GET). Or answer `GET /<name>` for `registry_packages.local` packages in our router, before verdaccio. Either way, npm-metadata would cost ~120 µs, saving ~6.6 of 30.3 (22%).

**Caveat:** skipping uplinks changes behaviour for a local package whose name also exists on npmjs, since npmjs versions are no longer merged in.

### 3. Turn off flexible checksums on both S3 clients (~5% of mix CPU now, ~8% of every remaining S3 read)

**Evidence:**

- `@aws-sdk/checksums` takes 8.0% of cdn-file and 8.5% of piece-bundle main-thread time: `flexibleChecksumsInputMiddleware`, `flexibleChecksumsResponseMiddleware` and `validateChecksumFromResponse`.
- The SDK default `responseChecksumValidation: "WHEN_SUPPORTED"` sets checksum mode on every GetObject and validates the body.

**Change:** add `requestChecksumCalculation: "WHEN_REQUIRED", responseChecksumValidation: "WHEN_REQUIRED"` to `new S3Client(...)` in `packages/registry/src/artifacts.ts:31` and in `packages/verdaccio-s3-storage/src/s3Client.ts:17`. This is a two-line change.

**Expected result:** it still pays off after #1, for npm-tarball, npm-metadata and cache misses.

### 4. Cache piece lookups and list pages in `Catalog`, and stop selecting search columns (5–9% of mix CPU; offloads Postgres)

**Evidence:**

- pg is 42–53% of main-thread time on piece-version, `/pieces`, `/packages`, package-detail and search.
- piece-version runs two uncached queries per request: `pieceOwner` (`packages/registry/src/catalog.ts:458`) and `pieceVersion` (`catalog.ts:448`), called from `middleware.ts:480` and `middleware.ts:485`.
- piece-bundle repeats `pieceVersion` through `pieceAt` (`middleware.ts:511`), at 27 µs/req of pg.
- `/packages` selects `search_doc` and `search_tsv` (`catalog.ts:89`) for every row, and the response discards them. `parseRow` and `utf8Slice` are 27% of that route's self time.
- `/pieces` returns each descriptor's full JSONB (`catalog.ts:405`), then keeps only counts and summaries.

**Change:**

- Cache `pieceOwner`, `pieceVersion` and `pieceLatest` rows in the same event-invalidated map as `#versions` (`catalog.ts:288`).
- Cache `sendPage` bodies and ETags (`middleware.ts:321`) per normalised query string for `/packages` and `/pieces`. Clear them on any registry event, with the 30 s TTL as a safety net.
- Drop `search_doc` and `search_tsv` from the outer select of `LISTED`, and keep them only in the `WHERE` and `ORDER BY`.

**Expected result:** saves ~2.7 of 30.3. Search is Postgres-bound, with Postgres at 2 cores and ~2.6 ms of Postgres CPU per search. A page cache there takes load off Postgres, not off the replica.

### 5. Stream without `stream/promises.pipeline` (~1.5% of mix; 3–3.6% of each streamed route)

**Evidence:** `DOMException` construction is 3.4% of cdn-file, 3.1% of piece-bundle and 3.6% of npm-tarball self time. On every finish, Node's `pipeline` aborts the `AbortController` it created, which builds a `DOMException` and captures its stack. The calls are in `stream()` (`packages/registry/src/middleware.ts:230`) and `readTarball` (`packages/verdaccio-s3-storage/src/s3PackageManager.ts:240`).

**Change:** use `src.pipe(res)` with `stream.finished` (callback form) for errors and cleanup. On cache hits, #1 removes the call entirely.

**Combined estimate:** #1, #3, #4 and #5 with the minimal form of #2 take the mix from ~0.30 to ~0.16 ms/req, about 1.9× the throughput per replica. With the fuller #2, it falls to ~0.11 ms/req, about 2.7×.

**Not worth chasing:**

- SHA-1 ETags (0.2%).
- Express routing itself (~3%).
- `writev`, the kernel send path. It grows only with the number of responses, not with code.

## Caveats

- **Host load:** macOS Docker Desktop VM with 18 CPUs, with a host load average of 5–9 from unrelated work during the runs.
  - With both replicas, NGINX and the generators busy, every area's cost per request grew about 1.5× compared with registry-1 loaded alone: 608 vs 379 µs of main-thread time.
  - Absolute µs therefore depend on contention. The relative breakdown held across runs, and every area scaled about the same.
- **Profiler overhead:** the inspector is enabled for the whole run, and sampling (500 µs) runs only inside the window. Profiled and unprofiled per-route runs differ by 0–9% (the table above). The mix via NGINX served 2,928 req/s with the profiler on and 3,412 req/s without it.
- **NGINX column:** divides requests evenly between the replicas, which is round-robin but was not measured.
- **Probe packages are tiny.** Real bundles and tarballs are larger, which moves cost towards byte streaming and makes #1's size cap matter.
- **npm metadata:** each read went to the real registry.npmjs.org. Its latency and CPU would differ behind a proxy, or with `PH_REGISTRY_LOCAL_PACKAGES` covering the names.
- **Scope:** cgroup CPU includes zlib (verdaccio's `compression`) and other threadpool work that the main-thread profile doesn't show. Only registry-1 was profiled.
