You've got documents. You've got operations. Now you need the outside world — a web app, a mobile client, an AI agent — to be able to read and write that data over the network. That's exactly what a <Term>subgraph</Term> does.

## One endpoint, many packages

Switchboard doesn't expose a single monolithic schema. Instead, every Reactor Package ships its _own_ GraphQL schema fragment — its subgraph. When Switchboard boots, it composes all of those fragments into one unified endpoint.

The practical payoff: a client can query data from two completely independent packages in a single request. Neither package knows about the other. Switchboard handles the stitching.

```graphql
query {
  todoList(id: "doc-123") {
    id
    todos {
      id
      title
      done
    }
  }
}
```

That query hits one endpoint. Behind the scenes, it's resolved by whatever package owns the `todoList` type.

## Subgraphs are the API face of your document model

If a document model defines the _shape_ of your data and the _actions_ allowed on it, the subgraph is how that shape appears to callers on the network.

Each subgraph exposes three things:

- **Queries** — for reading documents and processor read models.
- **Mutations** — for dispatching actions to documents.
- **Custom types** — domain-specific GraphQL types your resolvers return.

Because each package owns its subgraph, the package is the unit of delivery. Ship a new package and its API comes with it — no central schema registry to update.

## Authoring a subgraph

A package exports a class that extends `BaseSubgraph<Context>`. Its static name selects the route and its static `getSchema` declares the fields:

```typescript
import {
  BaseSubgraph,
  type Context,
  type SchemaBuilder,
} from "@powerhousedao/reactor-api";
import { ph } from "document-model";

export class TodoStatusSubgraph extends BaseSubgraph<Context> {
  static override readonly subgraphName = "todo-status";

  static override getSchema(schema: SchemaBuilder<TodoStatusSubgraph>) {
    return [
      schema.query("todoStatus", {
        returns: ph.String({ required: true }),
        resolve: ({ subgraph }) => subgraph.status(),
      }),
    ];
  }

  status(): string {
    return "ready";
  }
}
```

Resolvers read instance state through `subgraph`. The request context carries the caller, not a reactor client. Mutations authorize the caller, then use `subgraph.reactorClient` to dispatch document actions. The Reactor runs each action through its reducer, records the operation, and syncs it to peers.

A class returns typed entries or one `schema.graphql(...)` wrapper for SDL. To share behavior, extend an abstract base class or call a shared schema-building function. See [Inheritance and fragments](../../04-Reference/03-GraphQLData/08-SubgraphClasses.md#inheritance-and-fragments).

If your package was written before class-based subgraphs, run `ph migrate` before you build it. See the [migration guide](../../04-Reference/03-GraphQLData/07-SubgraphMigrationGuide.md).
