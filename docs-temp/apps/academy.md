# `@powerhousedao/academy`

`apps/academy` · **private** · v6.2.3-dev.9

The documentation site — https://academy.vetra.io

---

## Purpose

*"Comprehensive documentation and learning resources for the Powerhouse ecosystem."*

A [Docusaurus](https://docusaurus.io/) static site. The root README points at it as
the canonical developer documentation for Powerhouse Vetra.

It is `private: true` — never published to npm. The artefact is a deployed site.

---

## Functionality

### Content

| Path | Contents |
|---|---|
| `docs/academy/` | The main documentation tree: `00-Home.mdx`, `01-GetStarted`, `02-Learn`, `03-Build`, `04-Reference`, `05-Lookup`, `ReleaseNotes` |
| `docs/bookofpowerhouse/` | A separate long-form book |
| `slides/` | Marp slide decks (`slides:preview`, `slides:build`) |
| `src/` | `components/`, `css/`, `pages/`, `theme/` — Docusaurus swizzles and custom React |
| `vetra-design-system/` | Site-local design tokens |
| `static/`, `docusaurus.config.ts`, `sidebars.ts`, `babel.config.js` | Standard Docusaurus |

### Generated documentation — four scripts

`pnpm generate:docs` runs three of these in sequence:

| Script | Produces |
|---|---|
| `scripts/generate-combined-cli-docs.ts` | CLI reference from `ph-cli` / `ph-cmd`'s `COMMANDS.md` (themselves generated by those packages' `postbuild` steps) |
| `scripts/generate-recipe-docs.ts` | Recipe pages — the same recipes `test/recipes-e2e` executes |
| `scripts/generate-llm-docs.ts` | `static/llms.txt` and `static/llms-full.txt`, run by `build` |
| `scripts/check-doc-snippets.ts` | Verification, see below |

### LLM-optimised documentation

`pnpm generate:llm-docs` writes `static/llms.txt`, an [llms.txt](https://llmstxt.org)
index of every page, and `static/llms-full.txt`, every page concatenated. `build`
runs it first, so the deployed site serves both at its root and they always match
the deployed docs. Both files are gitignored.

`ACADEMY_LLM_COMPLETE.md` is an older single-file export. No script generates it.

### Running it

```bash
pnpm --filter @powerhousedao/academy dev     # docusaurus start --no-open
pnpm --filter @powerhousedao/academy build   # NODE_OPTIONS=--max_old_space_size=2048
pnpm --filter @powerhousedao/academy serve
```

The memory flag is needed for the size of the doc set. A `Dockerfile` and
`entrypoint.sh` are included, and `heroku-postbuild` maps to the build.

## Test infrastructure

**No Vitest, no test script, zero test files.** The verification is different in
kind:

### 1. The build is the test

The README: *"Build and serve locally before pushing — the build fails on broken
links."* Docusaurus link checking is the primary correctness gate.

### 2. `scripts/check-doc-snippets.ts`

`pnpm check:doc-snippets` — validates that code snippets embedded in the docs still
match reality. This is the guard against documentation drifting from the API.

### 3. `test/recipes-e2e`

A separate workspace package (`pnpm test:e2e:recipes` → `tsx scripts/run.ts`) that
**executes the recipes the academy documents**. If a documented recipe no longer
works, this fails. It is the strongest test the docs have.

### 4. `pnpm typecheck`

`tsc` over the site's own TypeScript.

### CI

| Workflow | Trigger |
|---|---|
| `.github/workflows/academy.yml` | Any push to `main` touching `apps/academy/**` → auto-deploy to **dev** |
| `.github/workflows/deploy-academy.yml` | Reusable; promotes to staging/production manually |

The README's deployment note: merging to `main` auto-deploys the dev site; staging
and production are promoted deliberately.

## How it is used

**It has no `workspace:*` dependencies and nothing depends on it.** It is entirely
decoupled from the code graph — which is why it can build and deploy on its own
workflow without the rest of the monorepo.

```mermaid
graph TD
    phcli["clis/ph-cli<br/>COMMANDS.md (generated)"] -. "scripts/generate-combined-cli-docs.ts" .-> academy
    phcmd["clis/ph-cmd<br/>COMMANDS.md (generated)"] -. .-> academy["apps/academy"]
    recipes["docs recipes"] --> academy
    academy -. "recipes executed by" .-> recipese2e["test/recipes-e2e"]
    academy -- "deploy" --> site["academy.vetra.io"]
    rb["reactor-browser<br/>ADR 0002 references<br/>04-Reference/08-ReactorBrowserClient"] -. "documented in" .-> academy
```

The couplings are by **content**, not by imports:

| Coupling | Detail |
|---|---|
| CLI docs | Generated from `ph-cli` / `ph-cmd`'s `COMMANDS.md`, which those packages regenerate in `postbuild` (via bun). Change a command, rebuild the CLI, regenerate here |
| Recipes | Documented here, executed by `test/recipes-e2e` |
| Reference pages | e.g. ADR 0002 designates `apps/academy/docs/academy/04-Reference/08-ReactorBrowserClient/` as the reader-facing restatement of `reactor-browser`'s client limitations |
| Release notes | `docs/academy/ReleaseNotes` alongside the repo-root `RELEASE-NOTES.md` (the `/release-notes` skill drafts into the latter) |

### Practical implication

Because the site is decoupled, **nothing in CI forces the docs to follow a code
change**. The two mechanisms that do are `check:doc-snippets` and
`test/recipes-e2e` — worth running when you change a public API or a CLI command.
